## 1. 主要功能实现

本 commit 在 `hccl/tools/diagnosis/` 下建立了 HCCL 步骤级离线诊断工具的第一个完整版本，对应迁移方案文档（[step-trace-causal-diagnosis-migration-plan.md](../hccl/docs/help/step-trace-causal-diagnosis-migration-plan.md)）第 6 节“离线工具迁移与完善”中规划的模块清单。

### 1.1 统一数据模型（[schema.py](../hccl/tools/diagnosis/schema.py)）

定义了三种数据视图的字段集和对应的 `dataclass`：

| 视图 | 字段数 | 说明 |
|---|---|---|
| `SEMANTIC_FIELDS` | 21 | 从 plog `[HcclTaskSemantic]` 解析出的语义字段 |
| `PROFILER_FIELDS` | 9 | 从 msprof `task_time.csv` 解析出的 profiler 字段 |
| `MERGED_FIELDS` | 30 | 合并后的输出字段，含 `match_status`、`duplicate_semantic`、`duplicate_profiler` |

关键设计点：

- `SemanticRecord` 和 `ProfilerTask` 均为 `frozen=True` 的不可变 dataclass，保证数据完整性；
- 两者均提供 `merge_key` 属性，统一返回 `(node_id, device_id, stream_id, task_id)` 四元组；
- 版本号 `SCHEMA_VERSION = 1` 已设置，为后续 schema 演进预留了接口；
- `parse_int()` 支持 `int(text, 0)` 解析，可自动识别十进制和十六进制；
- `first_present()` 按优先级查找多可能列名的值（兼容不同版本 msprof CSV 列名差异）；
- `normalize_task_kind()` 统一小写化 task_kind 字符串；
- `write_csv()` 使用标准库 `csv.DictWriter`，无外部依赖。

### 1.2 plog 解析器（[parse_plog.py](../hccl/tools/diagnosis/parse_plog.py)）

职责：从 HCCL 运行时日志中提取 `[HcclTaskSemantic]` 记录。

支持的格式（三种）：

1. `field=value` 格式（versioned key=value，新版标准格式）：正则 `KEY_VALUE_RE`
2. 旧版空格分隔的 legacy token 格式：11 个位置字段
3. 跨行 legacy 格式（标签行 + 值行）：`parse_legacy_block()` 内部迭代器处理

辅助能力：

- 自动从 plog 行前缀 `HCCL(pid,process):` 中提取 `pid`（通过 `PID_TS_RE` 正则）；
- `semantic_from_mapping()` 支持字段别名 fallback（如 `op_type`/`operation`、`user_rank`/`rank`）；
- `semantic_from_legacy_tokens()` 按固定位置解析旧格式。

CLI 入口：`python -m tools.diagnosis.parse_plog <plog> -o <output.csv>`

### 1.3 msprof 解析器（[parse_msprof.py](../hccl/tools/diagnosis/parse_msprof.py)）

职责：从 msprof 导出的 `task_time.csv` 解析 profiler 任务行。

关键行为：

- 跳过 `kernel_type == "PROFILER_TRACE_EX"` 的行（与迁移方案 5.4 节“不迁移 `aclprofMarkEx`”一致）；
- 使用 `first_present()` 按优先级匹配列名（支持 `device_id`/`Device_id`/`Device ID`/`device` 等多种写法）；
- `default_node_id` 参数支持为历史数据补充缺失的 node_id；
- `encoding="utf-8-sig"` 兼容 BOM 头的 CSV 文件。

CLI 入口：`python -m tools.diagnosis.parse_msprof <task_time.csv> -o <output.csv> [--node-id <id>]`

### 1.4 合并引擎（[merge_timeline.py](../hccl/tools/diagnosis/merge_timeline.py)）

职责：将语义记录与 profiler 任务按 `merge_key` 合并。

合并逻辑：

1. 首选键为 `(node_id, device_id, stream_id, task_id)`；
2. 对语义侧和 profiler 侧分别统计 duplicate key（`Counter`）；
3. 输出每行的 `match_status`（`matched` / `unmatched_semantic`）；
4. 追踪未被语义侧匹配的 profiler 行（`unmatched_profiler` 计数）；
5. 统计输出包含：`semantic_total`、`profiler_total`、`matched`、`unmatched_semantic`、`unmatched_profiler`、`duplicate_semantic_keys`、`duplicate_profiler_keys`。

CLI 入口：`python -m tools.diagnosis.merge_timeline --plog <...> --task-time <...> -o <...> [--node-id <...>] [--summary <...>]`

### 1.5 数据质量校验（[validate_trace.py](../hccl/tools/diagnosis/validate_trace.py)）

职责：校验合并后的输出 CSV 是否达到质量门禁。

检查项：

- 总行数 > 0；
- 匹配率 >= `min_match_rate`（默认 95%）；
- `duplicate_semantic` 和 `duplicate_profiler` 标记均为 0。

不符合条件时以非零退出码返回。

CLI 入口：`python -m tools.diagnosis.validate_trace <merged.csv> [--min-match-rate 95]`

### 1.6 单元测试（[test_diagnosis.py](../hccl/tools/diagnosis/test_diagnosis.py)）

覆盖范围（1 个 TestCase，1 个集成式测试方法）：

- plog 解析（2 条 fixture 记录）；
- msprof 解析（含 PROFILER_TRACE_EX 跳过验证）；
- 合并逻辑（验证匹配数为 2，duplicate 为 0）；
- 校验逻辑（验证 match_rate = 100%）；
- 字段解析断言（`pid`、`device_id`、`task_kind` 等）。

测试使用确定性 fixture 文件（[sample.plog](../hccl/tools/diagnosis/fixtures/sample.plog) 和 [task_time.csv](../hccl/tools/diagnosis/fixtures/task_time.csv)），可复现。

### 1.7 使用文档（[README.md](../hccl/tools/diagnosis/README.md)）

提供了简洁的模块说明和完整的命令行示例。

## 4. 可能的风险

1. **Fixture 与真实数据格式差距**：当前 fixture 仅覆盖 2 条记录，且使用了简化的 `field=value` 格式。如果真实 plog 使用旧版 `field[value]` 格式或其他非标准格式，解析器可能产生静默的字段缺失或误匹配。

2. **Legacy 格式的跨行解析脆弱性**：([parse_plog.py:54-72](../hccl/tools/diagnosis/parse_plog.py#L54-L72)) `parse_legacy_block()` 在标签行后通过 `next(iterator)` 取下一行作为值行，如果真实日志中标签行和值行之间存在其他日志行（如时间戳、线程 ID 等），会读到错误的数据。

3. **merge_key 的唯一性假设**：当前合并逻辑假设 `(node_id, device_id, stream_id, task_id)` 在 profiler 侧是一对一的。如果真实数据中存在一个 task_id 被多个 semantic scope 使用（task 复用场景），会产生错误的匹配。

4. **merge_key 仅使用第一个匹配**：([merge_timeline.py:42](../hccl/tools/diagnosis/merge_timeline.py#L42)) `matches[0]` 在有多个 profiler 匹配时只取第一个，未处理多匹配的歧义情况。虽然 `duplicate_profiler` 会在统计中记录，但合并结果中已经静默地选了一个。

5. **缺少 CI 集成**：当前单测可手动运行但未接入 CI pipeline，可能随着 plog 格式变化而腐化。

6. **无性能考量**：当前实现将全部数据加载到内存（`list(...)`），对于大规模 plog（如 commit 2 中提到的 143,282 条记录）可能内存压力较大，但当前阶段可接受。

7. **旧版单机数据的 node_id/device_id 缺失**：旧版 plog 不包含 `node_id` 和 `device_id`，当前解析器将这些字段设为默认值（`""` 和 `-1`），可能导致 merge_key 匹配失败。这是 commit 2 要处理的核心问题。

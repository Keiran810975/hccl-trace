### 1.1 旧版 `field[value]` 格式支持（[parse_plog.py](../hccl/tools/diagnosis/parse_plog.py)）

**问题**：真实 cann-hccl 的 plog 使用 `field[value]` 格式（如 `stream_id[12] task_id[34]`），而非 fixture 中的 `field=value` 格式。原解析器无法正确处理。

**方案**：

- 新增 `BRACKET_VALUE_RE = re.compile(r"([A-Za-z_][A-Za-z0-9_]*)\[([^\]]*)\]")` 正则；
- 新增 `_parse_bracket_values()` 函数，将 `stream_id[12] task_id[34]` 解析为 `{"stream_id": "12", "task_id": "34"}`；
- 在 `parse_plog_lines()` 和 `parse_legacy_block()` 中，`field[value]` 格式优先于 `field=value` 格式尝试；
- 如果两种格式都不匹配，则回退到 legacy token 格式。

```python
# parse_plog.py 中的优先级链：
# 1. _parse_bracket_values() → field[value]
# 2. _parse_key_values()     → field=value
# 3. semantic_from_legacy_tokens() → 空格分隔的固定位置
```

### 1.2 旧版单机 fallback 匹配（[merge_timeline.py](../hccl/tools/diagnosis/merge_timeline.py)）

**问题**：旧版 plog 没有 `node_id` 和 `device_id`，semantic 侧的 `merge_key` 为 `("", -1, stream_id, task_id)`，无法与 profiler 侧的 `("node0", 0, stream_id, task_id)` 匹配。

**方案**：

在 `merge_records()` 的主循环中增加了受控 fallback：

```python
# merge_timeline.py 第 43-48 行
if not matches and not semantic.node_id:
    device_task_matches = profiler_by_device_task_key.get(
        (semantic.device_id, semantic.stream_id, semantic.task_id), []
    )
    if len(device_task_matches) == 1:
        matches = device_task_matches
```

关键约束：

1. 仅当主键匹配失败**且**语义侧缺失 `node_id` 时触发；
2. fallback 键为 `(device_id, stream_id, task_id)`，去掉了 `node_id`；
3. **仅当 fallback 匹配结果为唯一一条时**才采用，避免多机误配。

这在旧版单机 8 卡场景下是正确的，因为此时 `device_id`（即 semantic 的 `rank`）与 msprof 的 `Device_id` 一一对应。

## 4. 可能的风险

1. **bracket 值的转义问题**：当前 `BRACKET_VALUE_RE` 使用 `[^\]]*` 匹配方括号内值，如果真实日志中字段值包含 `]` 字符（虽然极少见），会导致截断。

2. **fallback 的单机假设**：merge 的 fallback 逻辑仅在 `not semantic.node_id` 时触发，且要求 `len(device_task_matches) == 1`。这在以下场景中可能失效：
   - 多机场景中某个 rank 恰好只有一条 device_task_match（会错误匹配）；
   - 单机场景中旧版 profiler 有重复 task_id（会跳过 fallback，造成不匹配）。

   建议后续增加多机环境下的显式检查（如要求 `--single-node` flag 显式传入）。

3. **143K 记录的验证方式为抽样**：commit message 提到“没有整文件读取，只用 rg 抽样和解析统计”。这意味着可能存在未被抽样覆盖的边缘格式变体，后续使用完整数据时可能出现解析失败。

4. **`task_kind` 与 `task_type` 的语义重叠**：在 bracket 格式中，`task_type[5]`（数值）与 `task_kind[notify_wait]`（字符串）同时存在。当前解析器将两者分别映射到 `task_kind`（通过 `task_kind`/`task_type` 别名），但 `task_type[5]` 是数值 ID 而非语义名称。如果真实数据中只有 `task_type` 而没有 `task_kind`，会导致 task_kind 被填充为数值字符串而非语义名。

5. **`parse_plog_lines` 与 `parse_legacy_block` 的代码重复**：两个函数中 bracket/equals/legacy 的判断逻辑几乎一致（约 15 行），但 `parse_plog_lines` 使用 `pending_header` 机制而 `parse_legacy_block` 使用 `next(iterator)`，两套逻辑的演进可能不同步。

6. **无 `device_id` 但有 `rank` 的隐式映射**：([parse_plog.py:94](../hccl/tools/diagnosis/parse_plog.py#L94)) `device_id=parse_int(data.get("device_id", data.get("device", data.get("rank"))))`，将 semantic `rank` 映射到 `device_id`。当 profiler 侧的 `Device_id` 使用不同的编号体系时（如物理设备 ID 而非 rank），会产生错误匹配。目前单机场景中 rank=Device_id 成立，但多机或多 die 场景不成立。

# 单机21例定位失败复核与第一阶段修正

## 结论

采集和依赖构图通过，不等于自动定位通过。这批数据没有缺失HCCL语义：21例均为
142080/142080 exact。失败主要暴露了源头选择错误及库外原因的覆盖缺口。
原正式结果、21张HTML和压缩包不改写；本轮没有启动新设备实验或部署服务器源码。

## 从结果确认的问题

| 观察 | 证据 |
| --- | --- |
| 20个主候选全是任务前空隙，而非任务自身执行变慢 | `component=pre_task_gap`，20/20 |
| 有上游慢任务仍将下游空隙当源头 | 17/20个旧主候选的`upstream_slow_graph_ids`非空 |
| 时长标慢与gap混为一项 | 2/20同时`duration_slow=true`，均为Wait，旧输出只展示gap组件；不是额外证明Copy/Reduce源头 |
| Wait为自己的空隙提供零边路径支持 | 2/20的旧候选把自身计入受影响Wait |
| 主候选没有命中注入位置 | Rank和时间均不符11例、仅时间不符8例、仅Rank不符1例 |

例如延迟01实际在正式iteration37（第38轮）的Rank3调用前延迟71ms，旧主候选却是
iteration25的Rank1、约34ms的通信任务前空隙。旧排序取整个采集内最大的局部增量，
并未先确定故障事件，也不等价于找到对workload完成时间贡献最大的根因。

## 根本原因

1. `find_sources`允许gap绕过上游慢化检查，并且在同一任务同时执行变慢、空隙变长时只保留gap。
   图上存在一条可达路径就可以成为候选，没有要求路径最后真正经过该Wait的通知生产端。
   空隙没有已观测的执行主体，可能包含调度、未建模工作或传播阻塞，不能凭增量大就定为根因。
2. 原回溯和空隙计算仅在同一个operation内进行。当前定点延迟是AllReduce之前的Host sleep；
   公共调用`before`时间又记录在sleep之后，因此现有内部Task链没有那段Host工作。
3. GEMM等计算任务虽有部分profiler记录，但缺少当前诊断所需的轮次/调用语义绑定。
   未关联的计算任务不会进入现有按语义位置比较与溯源，计算导致的晚到可能断在通信入口。
4. 前5轮均值和无绝对下限对局部抖动敏感；全采集只挑一个最大增量还会让无关事件抢占主候选。
   修正归因不等于已经完成事件检测、误报控制或workload关键路径影响分析。
   现有关键路径模块是独立分析/导出，并未被`find_sources`用于主候选选择；此次compact运行也未导出它。

## 已实现的源头策略v2

- 保留原来的前5个正式iteration均值、1.5倍和3*MAD条件，不增加绝对下限，不修改评判标准。
- 将执行耗时和任务前空隙分成两个独立组件；空隙不会再覆盖同一任务的真实执行慢化。
- gap标记为`unattributed_gap`，保留为观察，不参与主根因选择，也不把Wait标成已解释。
- 执行候选必须有真实observed/exact路径，且最后一条边是生产端到目标Wait的Notify同步边。
  单纯流顺序可达、Wait到自身的零边路径都不提供根因支持。
- 上游gap或Wait不再直接隐藏下游任务自身的执行耗时增长。独立执行增长仍需自己的通知路径证据。
- JSON和流水线记录`source_policy_version=2`、gap观察数量及有支持的执行候选数量。

未新增/猜测依赖边，没有用异常类型、目标Rank或注入时间选择候选。
候选仍不等于已证明的物理故障类型；目前主候选排序仍不保证全workload的因果/关键路径结论。

## 验证边界

针对性回归覆盖大gap抢占、同一任务双组件、上游gap/Wait遮蔽执行候选、仅流顺序的伪支持、
Wait自支持及HTML诊断关联；162项相关回归通过。还回放了完整保留的正式尺寸正常预检：

| 指标 | 修正前 | 修正后 |
| --- | --- | --- |
| Task数 | 47064 | 47064 |
| 可比任务 | 3200 | 3200 |
| 标慢任务 | 726 | 726 |
| 有依赖支持的候选 | 308 | 15 |
| 单独保留的未归因gap观察 | 未区分 | 579 |

该数据是1预热+7测量的正常预检，不是20例异常的重新测试。
修正后正常样本仍产生候选，因此不能宣称误报已经消除，更不能用此数字声称新版准确率。
证据在`artifacts/diagnosis-source-review-20261025/`；原正式21例原始异常DB已按约定清理，
局部HTML缺少整段历史，无法据此完整重跑新算法。

## v3补充（第二次修改）

已实现公共Host准备记录、独立API/调用绑定，以及按本地调用事件和关键路径执行增量收益筛选
主源头。代码入口是`source_events.py`，集成于`rolling_diagnosis.analyze`及单机采集入口。
新策略仍不读取异常配置、目标Rank或注入时间，不修改同Rank且时间重叠的评判标准。
详见[滚动规则v3](rolling-diagnosis.md)。

正式尺寸正常预检与短通信正常预检回放均无主根因；可比/标慢数量分别仍为3200/726和296/63，
排除依靠提高task阈值达到这一结果。Host延迟和有关键路径影响的Copy通过合成回归，
没有公共Host记录、只有长Wait、无exact生产端证据、对完成时间无影响时仍保留未定位。
这是分析实现和正常数据回放，不是重新完成20例异常测试，原结果未改。

## v4补充（当前修复）

v3把“局部调用变慢、单任务有正关键路径收益”作为定位前提过强：并列慢路径或调用外的
传播可以使单任务收益为零，却不意味着没有异常源头。现将定位证据和影响度量分开，
影响为零/不可计算仍如实记录，不据此抹掉已支持的源头。

新增`wait_backtrace.py`，由慢Wait沿真实Notify生产端和流前驱反查，穿过正常但晚到的任务，
保留既有跨operation边。执行自身慢化可成为候选，空隙仍不是根因；多个分支分别保留，
对不相容时间、缺失语义、未配对和跨机时钟边界输出明确断点，不合成依赖。
结构化报告和原生等待HTML均展示覆盖率与断点；局部图和保留图包含完整选定路径。

运行控制也已修复：不再在正式轮次内阻塞等待后台进程校验/退出；窗口结束只请求停止，
worker暂停后等待正式测量完成才校验和销毁。新增活动窗口/授权时间校验，逐轮耗时与收尾
耗时分别保留。SDK替身下的原生worker生命周期测试不能代替CANN设备编译和NPU实测。

两个正常预检仍无主根因，task可比/标慢数量不变；现在分别记录117/19条慢Wait回溯及
`unresolved_waits`，不是宣称没有异常。旧20例缺完整原始历史，不能据此报新准确率。
本地测试和回放证据见[v4修复验收](../../../artifacts/diagnosis-source-policy4-20261025/README.md)。

## 第一阶段结束时记录的剩余问题（历史）

- 记录不含注入标签的Host准备/调用边界，将调用前延迟作为库外边界候选；需要准确到Host活动时，
  还要补相应观测，不能把一个宽空隙当作已确认的执行任务。
  v3已补公共准备区间，旧采集不能追补；宽区间仍不代表具体物理故障类型。
- 用可验证API/任务绑定把前置GEMM接到通信入口的真实依赖，避免把计算晚到误判成通信自身执行慢。
- 先定位异常轮次/调用事件，再在事件内回溯；加入本地关键路径/实际等待影响验证，控制正常抖动误报。
  v3已接入本地调用事件与关键路径敏感性，未证明全workload收益，也未完成独立异常准确率验证。
- 固定修正规则后重新采集代表性异常和独立正常/新随机样例，先验证再扩到完整测试集。
  不能看旧注入真值挑另一个候选，或事后放宽时间窗口来提高命中率。

更新：2026-10-22；代码分支：`nf`。本文说明实际环境、运行方式和测试集的验收标准。
仓库只发布源码、模板和文档；原始DB、日志、二进制、密钥和本地实验结果不随Git上传。

## 1. 先区分已经验证的两件事

| 实验 | 已验证 | 没有验证 |
|---|---|---|
| 正常小负载：2机4 Rank，每Rank 8MiB AllReduce，1轮预热+3轮测量 | 配套nf Host/Device加载、语义打点、msprof DB、精确合并、跨机依赖、等待分析及HTML；512/512语义exact、144条跨机边、496个paired Wait | 异常定位准确率、大负载完整诊断、四机 |
| 大负载短预检：2机4 Rank，8 Block，每Rank每轮7GiB输入，1轮预热+2轮测量 | 正常、20ms调用前延迟、1个Copy后台、1个计算后台、1组双端通信后台均执行成功并完成清理 | 本轮没有msprof采集和完整语义诊断；没有执行限速、正式50轮或完整异常矩阵 |

小负载完整诊断使用过已授权的临时开发验签设置，结束后已恢复原值和官方Device包。
大负载短预检使用官方Device包，不调整验签，不能把它记为“大负载诊断通过”。
详情分别见[小负载验收记录](../hccl/tools/diagnosis/nf-authorized-two-node-validation.md)和

## 4. Workload与测试集配置

主配置是Transformer形状的合成计算/通信负载，不是完整模型训练：
8 Block，tokens2048、hidden8192、FFN32768，BF16 GEMM/GELU；
每Block执行128/256/512MiB三个FP32 SUM AllReduce。
每轮24次业务collective、每Rank输入7GiB；该数不是网卡实际收发量。
每Rank BF16权重约14GiB，另有桶、激活、运行时和后台进程内存。

正式配置10轮预热+50轮测量；默认注入Rank2、第26个测量轮次、Block3、bucket1，
配置索引均从0开始。后台负载覆盖iteration25..29，调用前延迟只在指定桶注入一次。
正常组保留相同控制barrier。启动阶段另有2次配置检查AllReduce，不能算进业务调用序号。

| 异常 | 三档 | 注意 |
|---|---|---|
| progress_delay | 1/20/200ms | 默认arrival：通信调用前sleep，不是内部kernel延迟 |
| nic_limit | 正常配置带宽的75%/50%/25% | 需要真实RoCE限速query/apply/verify/restore接口 |
| copy_contention | 1/2/4个进程 | 每进程两个256MiB缓冲区；可能同时竞争搬运引擎和HBM |
| compute_contention | 1/2/4个进程 | 每进程BF16 4096x4096 GEMM |
| communication_contention | 1/2/4组 | Rank2与Rank0所在芯片，独立通信组持续256MiB AllReduce |

后台通信TCPStore使用29760起的端口；后台HCCL的Host/NPU监听设为`auto`，避免内部默认16666冲突。
共享物理芯片不等于已证明交换机拥塞；要称“RoCE网络拥塞”还需确认共享网络路径及计数器。
内部`library_task`延迟保留接口，但当前AI_CPU设备端注入未验收，不能填一个evidence字符串就宣称支持。

一个规模/位置/seed有1个正常样例+5类x3档，共16个计划样例。
3个规模、3个位置、3个seed共432个计划样例，不是已采集数量。
small/main/large每Block桶分别为32/64/128、128/256/512、256/512/1024MiB。

## 5. 双机启动方法

### 5.1 准备配置和计划

从仓库根目录生成，已存在目录拒绝覆盖；相同计划同步到两机：

```bash
"$PYTHON" test/two_node_suite.py generate --smoke --output /workspace/two-node-smoke
"$PYTHON" test/two_node_suite.py generate --output /workspace/two-node-core
cp test/configs/two_node_910c.example.json /workspace/two-node-cluster.json
```

站点模板带实际IP、runtime1/3及库路径，但`preflight_confirmed=false`。
完成占用/映射/兼容性/端口检查后，在本次运行配置中改为true，再将**同一份配置**同步两机。
不能只改本机条目，否则配置摘要检查会失败。
通信竞争还需在`shared_path_evidence`记录实测共享设备/路径及证据位置；不要伪造网络证据。
网卡限速还需现场`nic_limit`接口，详见[四机说明的接口合同](四机异常测试集与Workload说明.md#51-网卡限速接口)。

### 5.2 先短预检

在两个终端同时启动。Node0执行：

```bash
"$PYTHON" test/two_node_suite.py run-node \
  --case /workspace/two-node-smoke/cases/smoke-2n4r-main-i0-s20261022-normal.json \
  --cluster /workspace/two-node-cluster.json --node-rank 0 \
  --output /workspace/two-node-runs --attempt smoke-001 \
  --execute --no-profile --timeout 240
```

Node2使用完全相同命令，仅将`--node-rank 0`改为`--node-rank 1`。
两端case、attempt和配置一致；输出的node1目录表示torchrun第二节点，即物理Node2。
省略`--execute`只打印计划；`--no-profile`不采集DB，只验收启动、数值和清理。

接着分别将文件名后缀替换为`progress_delay-20`、`copy_contention-1`、
`compute_contention-1`、`communication_contention-1`。后三种两机均加`--allow-background`。
每次等两机完成后再跑下一例，重试使用新attempt，不覆盖失败证据。
不建议一次启动整个矩阵，避免多个case争抢同一设备和端口。

### 5.3 正式采集的前置条件

AI_CPU模式的语义执行点在Device端；**只设置HCCL_STEP_TRACE=1或替换Host库不够**。
要使用同一源码构建的nf Host/Device包，并确认Device实际加载。
HCOMM在`hcomm/`内执行`bash build.sh --pkg`等匹配环境的构建流程，不能用HCCL构建替代；
现有验证产物在`/workspace/nf-20261022/deploy/lib64`，新源码须重新核对构建和哈希。

现有官方Device包SHA256为
`d51cca4ff0d8b5e5e138be7541eac6f9c7b83079834ae4f9a74150c9b6aa9625`，
可做工作负载预检，但没有本项目Device语义扩展。
以前验收的自编译Device包为
`2b30fbe89be9eaa3c962f139aee162d356e97e1ce2b0788181d649d380f9974f`。
新构建哈希改变时重新记录，不能硬套旧值。

在管理员支持的签名/加载流程下部署；若再次使用临时开发验签，须满足本次授权与整卡空闲，
先快照、设置独立回滚、仅改自己的容器包、结束恢复并核对。验签设置是整卡范围：
chip1空闲而chip0有人运行时不能调整。这一流程不由公共测试runner自动执行。
此前保护脚本仅留在现场`authorized/device_guard.py`及本地原始证据中，不是仓库通用安装器。

正式记录至少确认Device初始化启用日志及`[HcclTaskSemantic] ... source[aicpu]`，
并通过下面的数据门禁；仅看到`AI_CPU`环境变量不算加载成功。

### 5.4 跑正常对照与异常样例

满足采集前提后，两端将短预检命令的case改为正式计划，**去掉`--no-profile`**：

```bash
"$PYTHON" test/two_node_suite.py run-node \
  --case /workspace/two-node-core/cases/2n4r-main-i25-s20261022-normal.json \
  --cluster /workspace/two-node-cluster.json --node-rank 0 \
  --output /workspace/two-node-runs --attempt capture-001 \
  --execute --timeout 1800
```

Node2仍只改node-rank为1。先验收normal，再跑同前缀的异常case；竞争类加`--allow-background`。
限速还需`--allow-network-change`和已核实的接口；没接口就跳过，不用普通Linux限速命令冒充RoCE限速。
baseline/fault要使用相同库、算法、选卡、消息规模、采集方式及seed，记录真实executor/transport。
为估计正常波动，建议先做至少3次独立正常运行，再做配对异常运行；这不是脚本自动重复功能。

每节点输出：

```text
<output>/<case-id>/<attempt>/node0或node1/
  environment.json             版本命令、设备快照、源码/库哈希
  execution.json               退出码、状态、DB数量
  ascend_log/                  前台Host/Device日志
  msprof/                      consolidated msprof_*.db
  private/case.json,cluster.json,command.json
  private/capture.log
  private/events/rank*/events.jsonl
  private/events/rank*/workload-result.json
  private/events/rank*/worker*/result.json
```

不要把后台进程的日志/DB混进前台诊断输入。msprof若采到后台子进程，需核对PID和设备，
保留前台正确的consolidated DB集合；当前解析器拒绝同一节点重复device采集。
不能为凑通过率任意删DB；无法可靠分离时，该采集不具备完整诊断验收条件。

## 6. 从采集到依赖和诊断

1. 将两机本次输出收集到一个分析目录，保留物理Node0/Node2、torchrun node0/1和Rank映射。
2. 参考`test/fixtures/multinode-run.example.json`创建本次manifest：`run_id`唯一，
   `nodes`指向前台plog/DB，`ranks`明确列出4个user_rank及本次实际runtime device_id。
3. `operations`绑定同一次collective的两端DB `(group_name, op_name)`，写明调用证据。
   业务还包含配置检查、warmup、barrier及层次子域；不能把“第N条DB记录”等同于第N个训练step。
   应核对`collective_submit`、通信域成员、算法日志和本地DB引用，再给共享调用标签。
   当前**没有训练型测试集的自动manifest生成器**；同名或时间接近不是绑定证据。
4. 初次核对可用`multi_node_trace`输出`operations.csv`辅助清点；缺绑定时可能退出非0，
   这不是成功结果。补齐有证据的清单后换新输出目录重放，原始DB保持只读。

```bash
python3 -m hccl.tools.diagnosis.multi_node_trace normal-run.json -o inventory
python3 -m hccl.tools.diagnosis.run_diagnosis normal-run.json -o replay-normal
python3 -m hccl.tools.diagnosis.run_diagnosis fault-run.json -o replay-fault \
  --baseline-dir replay-normal/NORMAL_RUN_ID --min-match-rate 95
```

将`NORMAL_RUN_ID`替换为正常清单的run_id；输出总在`<output>/<run_id>/`，不得复用已有目录。
分析机只需Python标准库。主要查看`pipeline_result.json`、`merge_summary.csv`、
`run_summary.csv`、`diagnosis_waits.csv`、`diagnosis_candidates.csv`及`waits.html`。
原始输入只接受consolidated DB和版本化plog，不使用导出JSON替代。

## 7. 什么才算样例通过

### A. 执行与注入通过：脚本确实干了预期的事

| 检查位置 | 条件 |
|---|---|
| 两节点execution.json | status=completed且returncode=0；无timeout、restore_failed |
| 四份workload-result.json | Rank0..3完整、world_size=4、status=passed、max_error=0，配置和设备正确 |
| arrival延迟事件 | 目标Rank、iteration/block/bucket命中一次，elapsed_ns不少于要求的延迟 |
| Copy/计算后台 | 目标芯片worker数量正确，operations>0、max_error=0、退出码0且按窗口停止 |
| 通信后台 | 两端各有要求数量worker，均实际执行、正常停止；还需核对共享路径 |
| 限速 | query原值、apply、verify与restore记录完整，作用于核实的RoCE端口，结束恢复原值 |
| 清理 | 自有容器没有残留训练/后台进程；Device包和临时验签已恢复，未影响他人任务 |

运行台账：

```bash
"$PYTHON" test/two_node_suite.py summarize --suite /workspace/two-node-core/suite.json \
  --runs /path/to/collected-two-node-runs --output /workspace/two-node-ledger.csv
```

应在两机输出汇总后运行，否则只有一个节点会标记partial。
`execution_complete`及`background_executed_effect_unverified`只表示A通过，**不表示竞争效果或诊断通过**。

### B. 数据与依赖通过：诊断有可信输入

| 检查位置 | 条件 |
|---|---|
| 两节点execution.json | 正式采集各有msprof_db_count>0；光有DB仍不够 |
| merge_summary.csv | 每节点semantic_total>0、exact_match_rate_percent>=95、merge_gate_passed=1；duplicate_semantic_keys、duplicate_profiler_execution_keys、duplicate_graph_correlation_keys、invalid_matches均0；ambiguous_semantic若有统计也须0 |
| run_summary.csv | graph_gate_passed=1、replay_gate_passed=1、cross_node_edges>0；cross_node_unresolved_channels及same_node_rdma_unresolved_channels均0 |
| 图artifact/问题表 | 无环、无缺端引用、无伪造配对；boundary数量逐个说明，不能套旧样例固定阈值 |
| pipeline_result.json | status=passed、analysis_completed=true，node_count=2，wait_count>0 |
| waits与HTML | 被评估传播链上的Wait为paired；peer_ranks、record_graph_ids和依赖边能回查原始输入，traversal_truncated=0 |

匹配率分母是已采集语义，不是所有硬件task；同时报告semantic_total、unmatched_profiler（profiler_only）和各阶段覆盖。
不能靠少采语义得到100%就认定完整。pipeline passed是数据处理通过，不是根因定位准确。

### C. 异常效果与诊断命中通过：找到对的慢点和传播关系

先确认注入确实产生可观测效果：相同任务/调用与正常参考比较，本地任务时长、等待或
对应iteration耗时超过预先冻结的正常波动阈值。不能只看全程平均值，也不能要求等待增量
恰好等于sleep时间。阈值应从独立正常样例标定，不能看完异常结果再挑阈值。

| 类型 | 期望核对的诊断证据 |
|---|---|
| 调用前arrival延迟 | 指定Rank/iteration/block/bucket的调用晚到及其下游等待；不能称定位到内部phase/step注入task |
| 内部task延迟（以后验证） | 命中日志、确切物理task及phase/step/event，与下游Wait的真实依赖路径 |
| Copy竞争 | 目标Rank的对应搬运任务变慢，沿实际依赖到peer Wait；不能仅凭D2D就归因于纯SDMA |
| 计算竞争 | 受影响的通信任务/调度与下游传播，结合后台计算及本地资源证据；不能把最长Wait直接叫根因 |
| 网卡限速/通信竞争 | 受影响跨节点调用和具体等待对端；声称网卡或网络拥塞根因时还需限速状态/网络计数器等独立证据 |

从`diagnosis_candidates.csv`检查候选Node/Rank、operation_scope、phase/step和原始graph_id；
从`diagnosis_waits.csv`检查`candidate_graph_ids`、`peer_ranks`、`record_graph_ids`、`evidence_path_edge_ids`、
`attribution`及`classification`。所有涉及的边都应存在于execution artifact。
`upstream_rank_operation_correlation`是同Rank/调用相关性，**弱于**`dependency_path`，不要作为精确因果边计分。

当前诊断有以下限制，必须保留在结果中：

- 默认长Wait阈值1ms，慢任务阈值5ms，并要求相对结构匹配baseline中位数至少3倍。
  小于这些门槛的1ms注入、几十微秒Copy变慢或2倍竞争可能不产生候选。
  当前CLI没有slowdown_factor选项；不能只降低绝对门槛就宣称解决该问题。
- 慢任务候选目前覆盖sdma、reduce_inline、kernel_aicpu及观测到的CPU build span，
  按持续时间排序，不是已验证的根因置信度排序；baseline按结构签名聚合，不是精确iteration一一对齐。
- Host调用前sleep不一定留下可归因到具体内部task的记录。
  能看见长Wait却不能解释上游来源时，只能记为等待发现，不算精确根因命中。
- RDMA task时长是门铃提交，不是网络传输完成时间；不据此直接算网络带宽或拥塞延迟。
- 跨机时钟未校准，只能比较各节点本地duration和依赖拓扑；不做跨机绝对时间相减。
  关键路径当前是node-local且可能partial_evidence，不等于整个训练workload的全局完成时间。
- 目前没有自动对照私有注入真值并输出整套准确率的评分器。case/events是评估真值，
  不能传给诊断器当答案；需独立核对后记录case结论，不把candidate_count>0直接当成功。

推荐给每例单独记录：`execution_pass`、`data_pass`、`effect_observed`、
`detection_pass`、`root_rank_hit`、`root_task_hit`、`propagation_verified`及失败原因。
ground truth粒度按注入机制定义；不支持task真值的arrival样例，其root_task_hit记N/A而不是强算正确。
诊断漏检是评估结果，不得将有效但未检出的异常样例从分母删掉。

批量报告至少分开统计：执行/采集失败率、有效异常的检出率、正常样例误报率、根因Rank命中率、
具备task真值样例的task命中率及传播边核验结果；另列因没有产生可观测异常而失效的注入。
如报告Top-1/Top-3，须说明当前使用的候选排序与评分规则，不能把所有候选都算一次命中。
“准确率90%以上、误报率低于10%”目前是目标，不是已测结论。

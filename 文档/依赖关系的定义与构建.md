# HCCL Trace 依赖关系的定义与构建

## 1. 本文要回答的问题

依赖图不是简单地把时间上相邻的任务连接起来。它必须回答四个不同层次的问题：

1. **执行事实是什么**：设备上实际执行了哪些 SDMA、Reduce、Notify 等任务？
2. **任务为什么存在先后关系**：来自物理 stream、FFts graph 声明、Notify 同步，
   还是 HCCL 算法语义？
3. **哪些关系足够精确**：哪些是 exact/observed，哪些只是 semantic，
   哪些信息不足而必须保留为 ambiguity？
4. **如何用于诊断**：如何从完整的控制执行图，得到适合关键路径和等待分析的资源图？

当前实现的核心原则是：

> execution graph 保存事实，resource graph 提供性能解释；任何性能解释都必须能反查事实，
> 不能用“时间最近”填补缺失的因果证据。

当前 graph artifact schema 为 **v4**。

## 2. 总体数据流

```text
HCOMM 语义插桩 plog                    msprof consolidated DB
[HcclTaskSemantic]                    TASK / COMMUNICATION_TASK_INFO
[HcclTaskGraphCorrelation]            COMMUNICATION_OP / STRING_IDS
          │                                      │
          └──────────┐                ┌───────────┘
                     ▼                ▼
                       merge_timeline.py
                     semantic ↔ physical task
                               │
                               ▼
                            merged.csv
                               │
                  ┌────────────┴────────────┐
                  ▼                         ▼
          execution graph             merge 质量门禁
     物理任务 + 控制任务 + 事实边       validate_trace.py
                  │
                  ▼
          deterministic contraction
                  │
                  ▼
           resource graph
        资源任务 + 收缩后的依赖边
                  │
       ┌──────────┼───────────┐
       ▼          ▼           ▼
   CSV artifact  HTML/SVG   graph gate
                            validate_dependency_graph.py
```

### 2.1 两个事实源的职责

| 数据源 | 提供的信息 | 不承担的职责 |
|---|---|---|
| HCOMM plog | algorithm、phase、step、slice、event、rank/peer、logical stream、FFts context/graph | 不提供设备任务真实起止时间 |
| msprof DB | device、physical stream/task、subtask/context、connection、真实起止时间、Notify ID/rank、operation metadata | 不直接解释 HCCL phase/step 的算法含义 |

两者在 `merged.csv` 中对齐后，依赖构建才能同时获得：

- profiler 的物理执行事实；
- HCOMM 的算法语义；
- DB 中的 Notify 与 collective operation 元数据。

## 3. 必须先区分的身份

依赖构建中最容易出错的地方，是把“执行任务”“Notify 存储”和“一次同步”当成同一个身份。
当前实现明确区分以下层次。

### 3.1 Physical execution identity

单机物理执行节点身份为：

```text
(node_id, device_id, physical_stream_id,
 task_id, subtask_id, connection_id)
```

生成稳定摘要：

```text
graph_id = x_<sha256-prefix>
```

字段作用：

| 字段 | 作用 |
|---|---|
| `node_id` | 限定节点时钟域和输入来源 |
| `device_id` | 区分同节点不同芯片，不能由 rank 推断 |
| `physical_stream_id` | 设备实际执行 stream |
| `task_id` | stream 内 profiler task 标识 |
| `subtask_id` | FFts 内部 context；direct task 为 `-1` |
| `connection_id` | 补足同一 profiler 执行身份，防止本地物理任务碰撞 |

开始时间、结束时间、CSV 行号不进入身份，因为它们是观测值，不是任务本体。提高时间精度或
重排 CSV 不应改变节点 ID。

`connection_id` 只参与物理 execution identity，**不参与 Notify relation identity，
也不能用来连接跨 rank 同步**。

### 3.2 Collective operation scope

collective invocation 的当前身份来自 msprof DB：

```text
(group_name, op_name)
```

公共 artifact 不暴露原始字符串，而输出稳定摘要 `profiler_op_scope`，并附带：

- `unique`：本地 DB 引用与该 scope 一一对应，可参与精确分区；
- `missing`：缺少 operation metadata；
- `ambiguous`：本地映射不是一一对应，不得参与 exact 构边。

`group_name` 用于区分不同通信域；只使用 `op_name` 会有通信域短 hash 碰撞风险。
DB 中的本地 `opId` 或 operation connection 只用于验证 join，不是跨 device 身份。

当前一次分析输入必须属于同一个 profile run。未来合并多次采集时，还需要外层
`profile_run_id`，防止相同 `(group_name, op_name)` 跨采集碰撞。

### 3.3 Notify resource identity

Notify resource 表示一块可复用的同步存储：

```text
(node_id, notify_id)
```

它只能回答“使用了哪块 Notify 资源”，不能回答“这是第几次同步”。同一 `notify_id`
会跨 step、graph launch 和 collective operation 复用。

### 3.4 Notify relation identity

Notify relation 表示一次 producer → consumer 的状态转换。它必须在 Notify resource
之外增加 operation、方向和 occurrence 序列。

FFts relation：

```text
(node_id, operation_scope, user-rank domain,
 producer_rank, consumer_rank, signal_kind,
 phase, step, slice, notify_id,
 sequence_kind=ffts_graph_instance, graph_instance_id)
```

Direct relation 分成两层：

```text
channel =
  (node_id, operation_scope, user-rank domain,
   producer_rank, consumer_rank, notify_id)

relation =
  (channel, sequence_kind=db_notify_ordinal, ordinal)
```

因此：

- `notify_id` 是资源，不是 occurrence；
- `db_notify_ordinal` 是同一 direct channel 内第几次状态转换；
- `graph_instance_id` 是 FFts relation 的 occurrence 分区；
- phase/step/slice 在 direct 路径中只作为语义 annotation，不替代 DB 物理 occurrence。

### 3.5 step 是因果桶，不是身份

当前 single-ring direct RS/AG 将 `step` 定义为 phase 内的逻辑因果桶：

```text
step 0       = round 0 的 init/prelude + main round 0
step 1..N-2  = main round 1..N-2
step N-1     = final/epilogue
```

因此多个 physical task、stream、event 或 slice 共享一个 step 是合法情况。特别是
RS step 0 可以同时包含主/从流 init copy 和 main round-0 task。不能把重复
`(phase, step)` 或 `(phase, step, slice)` 当成 duplicate execution。

step 也不能承担 collective occurrence identity。正确的理解是：

```text
physical identity 解决“这是哪个执行 task”
operation/graph/ordinal 解决“这是第几次执行或同步”
phase/step/slice 解释“该执行在算法中的什么位置”
```

对 FFts Notify，step 是 relation identity 的语义坐标之一，但仍必须有
`graph_instance_id`；对 direct Notify，step 只是 exact DB relation 的 annotation；
任何路径都不得只凭 step 建边。

`validate_trace.py` 目前只对已明确合同的 `reduce_scatter_direct/allgather_direct`
校验 `0 <= step < rank_size`，并禁止 ACK/payload/data-signal 出现在
`step=rank_size-1` 的 epilogue 桶。未知 phase 不套用 Ring 规则；冲突会输出 CSV
行号、物理 task 坐标和完整 phase/step/rank_size/slice/event，不按时间或邻接修正。

## 4. 节点模型：execution graph 与 resource graph

### 4.1 为什么使用两层图

Notify、event、profiling enable/disable 等任务是真实执行的控制原语，应保留在事实图中；
但它们不是数据搬运或计算资源本身，不适合作为资源关键路径中的主要节点。

因此当前实现使用两层图：

| 图层 | 节点 | 主要用途 |
|---|---|---|
| execution graph | 每个有时间信息的 profiler physical execution，包括控制任务 | 保留完整执行事实、构边证据和审计路径 |
| resource graph | `sdma/rdma/reduce_inline/reduce_tbe`，以及必要 boundary | 关键路径、同步等待、资源瓶颈分析 |

execution graph 是唯一事实层；resource graph 必须从 execution artifact 确定性派生，
不能读取原始输入后在可视化阶段重新推断。

### 4.2 execution node 的来源

进入 execution graph 的 `merged.csv` 行必须满足：

- `match_status` 为 `matched` 或 `profiler_only`；
- 具有有效 `task_start/task_stop`；
- physical execution identity 在输入中唯一。

`unmatched_semantic` 没有已认领的物理执行，不作为 execution node。

这解释了 `profiler_only` 节点存在的原因：它们是 DB 中真实存在但当前没有 HCOMM 语义声明的
控制或执行任务。忽略它们会破坏物理 stream 顺序和 Notify 完整序列。

### 4.3 resource node 的来源

当前资源任务采用显式白名单：

```text
sdma, rdma, reduce_inline, reduce_tbe
```

其他 task kind 不会自动提升为资源节点。未来若要加入 AI Core compute 或新的 transport
primitive，必须先明确其资源语义并扩展白名单，不能把所有未知 task 都默认当作资源。

真实 resource node 直接复用 execution `graph_id`，因此两种视图可以互相定位。

### 4.4 boundary node

若某条已确认的同步/语义边一侧找不到可达资源任务，resource graph 生成 boundary：

```text
boundary_id =
  hash(graph_schema_version, source_execution_edge_id, relation_id, side)
```

boundary 表示“依赖越过当前资源图覆盖边界”，不是设备真实任务。它保存：

- `boundary_side`：`upstream` 或 `downstream`；
- `boundary_reason`；
- `boundary_relation_id`；
- 与相邻控制端点一致的 node/device/stream 和边界时刻。

如果存在多个资源候选，则不生成 boundary，也不做候选笛卡尔积，而是输出 contraction
ambiguity。

## 5. execution graph 的依赖边分类

当前默认 execution graph 只有五类边。

| 边类型 | 含义 | 证据等级 | 当前样例数量 |
|---|---|---:|---:|
| `direct_stream_order_observed` | direct task 在同一物理 stream 上的可证明先后 | observed | 27,512 |
| `ffts_logical_stream_order` | 同一 FFts logical stream 中相邻 context 声明序 | semantic | 13,735 |
| `ffts_notify_sync_observed` | 唯一 FFts Notify producer → consumer | observed | 4,676 |
| `direct_notify_sync_exact` | DB channel 内按两侧本地 ordinal 对齐的 Notify | exact | 5,376 |
| `local_notify_sync_exact` | device-local channel 内按两侧 stream ordinal 对齐的 Notify | exact | 5,376 |

### 5.1 Direct physical stream 顺序

适用条件：

```text
subtask_id < 0
```

分组键：

```text
(node_id, device_id, physical_stream_id)
```

构建规则：

1. 用 DB 十进制精确时间按 `task_start` 分 bucket；
2. 同起始时间 bucket 内不建立顺序，避免对可能重叠的任务强行排序；
3. 只连接相邻 start bucket；
4. 仅当 `src.stop <= dst.start` 时建立边。

该边表达 profiler 已观测到的同一物理 stream 先后，不表达跨 stream 依赖。

### 5.2 FFts logical stream 声明序

FFts parent 下的 subtask 不能按 parent physical stream 强行串行，因为 graph 内部任务可能由
内部依赖控制或重叠执行。

候选必须满足：

- `match_status=matched`；
- `subtask_id >= 0`；
- semantic `ffts_ctx_id == profiler subtask_id`；
- operation scope 为 `unique`；
- pid、graph instance、parent stream/task、semantic logical stream 全部有效。

分组键：

```text
(node_id, device_id, pid, operation_scope,
 graph_instance_id, parent_stream_id, parent_task_id,
 semantic_logical_stream_id)
```

组内按 context ID 连接相邻声明；重复 context 是硬错误。

需要强调：该边只表示**同一语义 logical stream 的 context 声明序**，不声称两个 FFts
context 在硬件时间上完全不重叠。旧的 FFts parent physical-stream 全序已删除。

### 5.3 FFts Notify 同步边

语义事件先规范化为 producer/consumer：

| task kind + event | role | signal |
|---|---|---|
| `notify_record + tx_ack_start` | producer | ACK |
| `notify_wait + rx_ack_start` | consumer | ACK |
| `notify_record + tx_data_signal_start` | producer | data signal |
| `notify_record + tx_payload_start` | producer | data signal |
| `notify_wait + rx_data_signal_start` | consumer | data signal |

然后按完整 FFts `NotifyRelationIdentity` 分组：

- 恰好 1 producer + 1 consumer：生成 `ffts_notify_sync_observed`；
- 只有 1 个 endpoint：记为 `single`，不生成边；
- 多 producer/consumer：记为 `ambiguous`，不排序、不 zip；
- 身份字段缺失：记为 `incomplete`。

当前样例有 4,676 条 observed edge 和 28 条 single；ambiguous/incomplete 为 0。
`single` 是可见的不完整事实，目前不作为图门禁失败项。

### 5.4 Direct Notify exact 同步边

Direct Notify 以 msprof DB 的 canonical 字段为主：

- `task_kind`：record 或 wait；
- `notify_id`；
- `srcRank/dstRank` 规范化后的 producer/consumer 方向；
- `(group_name, op_name)` 派生的 operation scope。

`dstRank=-1` 表示本地控制 Notify，不进入这个跨 rank channel，而由下一节的本地
Notify builder 单独处理。

对每个 direct channel，只有同时满足以下条件才构边：

1. producer 和 consumer 都存在；
2. producer 只落在一个本地 physical stream；
3. consumer 只落在一个本地 physical stream；
4. 两侧 record/wait 数量相同；
5. 两侧各自的本地执行顺序唯一。

随后分别按两侧本地顺序排序，用相同 `db_notify_ordinal` 对齐。这里比较的是每一侧内部顺序，
**不比较 producer 与 consumer 的跨设备绝对时间**。

语义信息只做 annotation 与一致性检查：

- `both`：两端语义存在且一致；
- `partial`：只有一端语义；
- `none`：两端都没有语义，DB occurrence 仍然完整；
- `conflict`：语义方向或坐标与 DB relation 冲突。

当前 5,376 条 exact 边中：both 4,695、partial 9、none 672、conflict 0。

### 5.5 主从流本地 Notify exact 同步边

本地 Notify 的 DB 特征为 direct task 且 `dstRank=-1`。它不表示“缺少 peer”，而是同一
device 内两个 physical stream 之间的控制同步。channel identity 为：

```text
(node_id, operation_scope, device_id, notify_id)
```

其中 `device_id` 必须来自 profiler，不能由 `user_rank` 推断。Record 是 producer，Wait
是 consumer；两端各自必须只落在一个 physical stream，数量相等且各 stream 内执行顺序
唯一。之后分别对两侧编号：

```text
Record[ordinal] -> Wait[ordinal]
sequence_kind = db_local_notify_ordinal
edge kind = local_notify_sync_exact
```

该规则只使用两条 stream **各自内部**的 DB 顺序，不要求 `wait.start > record.stop`，也不按
跨 stream 最近时间配对。因此既支持 main→slave，也支持 slave→main；数量不等、多 stream、
顺序不唯一或 operation scope 缺失时整组写入 Notify ambiguity artifact，不做 `zip(min)`。
本地 relation identity 为：

```text
(local channel identity, db_local_notify_ordinal)
```

msprof 的 local `notify_id` 在当前数据中以接近 `UINT64_MAX` 的十进制值出现，CSV 读取必须
先按整数文本精确解析。若先经过 IEEE-754 `float`，超过 `2^53` 后不同 Notify resource 会
碰撞；本实现已用宽整数回归测试固定这一点。

当前样例有 112 个完整 local channel，每组 48 Record + 48 Wait：`45→13` 与 `13→45`
各 56 组，共生成 5,376 条 `local_notify_sync_exact/exact`，ambiguity/incomplete/conflict
均为 0。resource 收缩得到 5,376 条 `resource_local_notify_sync_exact`；其中每个 device
最初一条 slave→main relation 没有可达的上游资源任务，因此显式保留 8 个 upstream
boundary，而不是伪造资源节点。

### 5.6 已删除 Peer payload semantic 因果边

原 builder 曾将 `tx_payload_start` 与 `rx_payload_reduce_start/rx_payload_copy_start` 按
peer、phase group、step、slice 和 occurrence 顺序连接为 `peer_payload_semantic`。
当前样例的 2,142 条边经传递约简审计后结果如下：

- 删除 payload edge 后，2,142 个 `src → dst` 全部仍然可达；
- 0 条可以只靠 stream edge 到达；
- 2,142 条都通过恰好一条 `direct_notify_sync_exact` 到达；
- 所有最短替代路径长度均为 4，结构为
  `direct_notify_sync_exact -> direct_stream_order_observed × 3`；
- 0 条使用 `local_notify_sync_exact`。

因此这些边没有增加新的因果可达关系，同时 occurrence 只有 semantic/出现顺序证据。
`peer_payload_semantic` 与派生的 `resource_payload_semantic` 已从默认 execution/resource
因果图正式删除，并加入门禁禁用 kind。`tx/rx_payload_*` 事件和节点语义仍然保留；若未来
需要数据血缘展示，应使用独立 relation artifact，不重新混入因果 DAG。

## 6. 明确禁止的默认依赖

以下边不会进入默认因果图：

| 禁止规则 | 原因 |
|---|---|
| connection ID 相同即认为 Notify 对应 | connection 是 profiler 本地关联，不是同步 token |
| record/wait 时间最近配对 | 时间精度、并发和跨设备时钟会改变结果 |
| 相同 notify ID 直接全局配对 | Notify resource 会复用，不表示 occurrence |
| FFts parent physical stream 全序 | parent 下不同 logical stream/context 可能重叠 |
| 上一步/右邻居/phase bridge | 属于算法假设，不是 profiler 观测事实 |
| ACK/data signal 再生成 peer signal 边 | 与 exact Notify 控制边重复 |
| peer payload semantic 因果边 | 当前 occurrence 不精确，且样例中 100% 为 Notify+stream 传递冗余 |

门禁显式要求以下伪边数量为 0：

- `ffts_physical_stream_order`；
- `notify_sync_inferred`；
- `peer_signal_semantic`；
- `peer_payload_semantic`；
- `resource_payload_semantic`；
- 名称包含 `time_inferred` 的默认边。

## 7. 边身份、字段与证据等级

### 7.1 稳定 edge identity

```text
(graph_schema_version, edge_kind,
 src_graph_id, dst_graph_id, relation_id)
```

生成：

```text
edge_id = e_<sha256-prefix>
```

reason、evidence、时间和 CSV 行号不进入身份。所有 artifact 按稳定 ID 排序，CSV 行序不表达
occurrence。

### 7.2 关键边字段

| 字段 | 作用 |
|---|---|
| `kind` | 依赖类型，决定其构建规则 |
| `src/dst` | 稳定节点 ID |
| `reason` | 人可读的构边原因 |
| `evidence` | 使用了哪类物理/语义证据 |
| `confidence` | exact、observed、semantic 等证据强度 |
| `relation_id` | Notify occurrence 或收缩路径身份 |
| `sequence_kind/value` | occurrence 的序列来源和值 |
| `semantic_status` | DB relation 与 semantic 的覆盖/冲突状态 |
| `signal_kind` | ACK 或 data signal |
| `phase/step/slice` | 语义 annotation，不替代物理 identity |

### 7.3 证据等级

| 等级 | 含义 | 当前例子 |
|---|---|---|
| `exact` | identity 与 occurrence 规则完整，无候选歧义 | direct/local Notify DB ordinal |
| `observed` | profiler/共享 relation 唯一观测到的关系 | direct stream、FFts Notify |
| `semantic` | HCOMM 显式声明的逻辑关系 | FFts logical order |
| `inferred` | 受约束但未显式声明的推导 | 默认图当前不使用 |
| `heuristic` | 最近时间、出现顺序猜测 | 禁止进入默认图 |

证据等级不是“边是否有用”的评分，而是说明可以对该边做多强的因果陈述。

## 8. resource graph 的确定性收缩

### 8.1 收缩目标

execution graph 中常见控制链：

```text
resource_before
  -> notify_record
  -> notify_wait
  -> resource_after
```

resource graph 将其表示为：

```text
resource_before
  == resource_notify_sync_* ==>
resource_after
```

但不会丢弃证据。派生边保存：

- `source_execution_edge_ids`；
- `control_graph_ids`；
- `record_graph_id`；
- `wait_graph_id`；
- 原始 `relation_id/evidence/confidence/semantic_status`。

### 8.2 Frontier 搜索

资源收缩只沿 execution graph 的两种 order edge 搜索：

```text
direct_stream_order_observed
ffts_logical_stream_order
```

对同步边：

1. 从 source 控制端点沿 order edge 反向搜索；
2. 遇到第一个 resource task 即形成 upstream frontier，并停止穿越该分支；
3. 从 destination 控制端点沿 order edge 正向做相同搜索；
4. 两侧各只有一个 frontier 时，生成收缩边；
5. 某侧没有 frontier 时生成 boundary；
6. 任一侧有多个不同 resource frontier 时输出 ambiguity，不生成边。

如果多个控制路径最终汇入同一个 resource frontier，路径上的 execution edge/control ID
会合并保留，不会因为分支而丢失审计证据。

### 8.3 Resource order edge

从每个资源节点沿 order edge 正向搜索下一个资源 frontier，中间控制任务被收缩：

- 全部来自 direct order：`resource_stream_order_observed`；
- 全部来自 FFts order：`resource_ffts_order_observed`；
- 混合路径：`resource_order_observed`。

路径使用全部 source execution edge ID 生成稳定 `relation_id`。

当前实现这里存在一个需要修正的证据等级问题：源
`ffts_logical_stream_order` 的 confidence 是 `semantic`，但派生的
`resource_ffts_order_observed` 当前被写为 `observed`；混合路径也会统一写为
`observed`。确定性收缩只能保持或降低证据强度，不能把 semantic 提升为 observed。
下一版应引入 evidence lattice，按路径最弱证据传播，并相应调整 kind/schema。

### 8.4 Resource sync edge 映射

| execution edge | resource edge |
|---|---|
| `direct_notify_sync_exact` | `resource_notify_sync_exact` |
| `local_notify_sync_exact` | `resource_local_notify_sync_exact` |
| `ffts_notify_sync_observed` | `resource_notify_sync_observed` |

真实资源端点继续使用 execution `graph_id`；只有 boundary 使用 `b_` 前缀的派生 ID。

## 9. Notify 等待指标与边权

同步边输出以下纳秒指标。

### 9.1 wait_span_ns

```text
wait_span_ns = max(0, wait.stop - wait.start)
weight_ns = wait_span_ns
```

该值完全来自 wait 节点自己的本地时间区间，是当前 resource Notify edge 的等待权重。
由于 Notify wait 节点已经从 resource graph 中移除，关键路径计算不能再额外累加同一个
Notify wait duration，否则会重复计费。

### 9.2 remote_block_ns 与 post_signal_ns

同一 `node_id` 内，以 record 完成时刻切分 wait span：

```text
remote_block_ns =
  clamp(record.stop - wait.start, 0, wait_span)

post_signal_ns =
  wait_span_ns - remote_block_ns
```

它们是围绕 `record.stop` 的**观测分解**：

- `remote_block_ns`：wait 开始后、record 完成前的区间；
- `post_signal_ns`：record 完成后，wait 尚未结束的区间。

`record.stop` 不一定等于硬件 Notify 对 consumer 可见的精确瞬间，因此这两个值适合定位
等待构成，不应解释为协议内部绝对延迟。

### 9.3 handoff_gap_ns

```text
handoff_gap_ns =
  max(0, downstream_resource.start - wait.stop)
```

仅当 wait 与下游真实资源节点属于同一 `node_id` 时输出。它表示同步结束后到下游资源任务
开始前的空隙，可用于发现调度、stream 排队或 host/device handoff 延迟。

### 9.4 时钟边界

- 同节点：`timing_status=same_node_observed`；
- 跨节点且无时钟校准：
  `timing_status=cross_node_uncalibrated`，
  `remote_block_ns/post_signal_ns` 留空；
- 非 Notify 边：`timing_status=not_notify_sync`。

跨节点时仍可报告 wait 自己的本地 `wait_span_ns`，但不能把不同节点的绝对时间直接相减或
把这些权重当作全局可比较时钟。

## 11. 完整性与质量门禁

### 11.1 Artifact 导出硬错误

以下问题会阻止导出：

- duplicate node ID；
- duplicate edge ID；
- missing source/destination；
- self-loop；
- execution graph 存在 cycle 时禁止继续收缩 resource graph。

### 11.2 Dependency gate

```bash
python -m tools.diagnosis.validate_dependency_graph dep_graph \
  --max-boundary-nodes 8 \
  --summary-output dep_graph_gate_summary.csv
```

当前样例的 8 个 boundary 是每个 device 最初一条 slave→main local Notify relation 缺少
上游资源任务的显式边界；不是 missing edge endpoint。其他输入应按其已解释的 golden
设置上限，不能把 `8` 当作通用常量。

门禁检查：

- execution/resource duplicate、missing endpoint、self-loop、cycle；
- Notify `ambiguous/incomplete/conflict`；
- resource contraction ambiguity；
- boundary 上限；
- 禁止的 FFts 伪顺序、time-inferred、旧 Notify inferred 边；
- stream/sync 分类数量和已删除 payload kind 的零值。

`--golden-summary` 可固定预期统计；golden 变化应先解释构边合同或输入变化，再更新基线。

## 13. 如何利用依赖图做性能诊断

### 13.1 从 resource graph 开始定位瓶颈

resource graph 适合回答：

- 哪个 SDMA/RDMA/Reduce task duration 最长；
- 哪条 Notify 同步边 `wait_span_ns` 最大；
- 等待主要发生在 record 完成前，还是完成后的 post-signal 区间；
- wait 结束后是否存在较大的 `handoff_gap_ns`；
- 某个资源任务是否拥有异常多的前驱或后继。

### 13.2 回到 execution graph 解释原因

找到异常 resource edge 后，使用：

- `source_execution_edge_ids`；
- `control_graph_ids`；
- `record_graph_id/wait_graph_id`；
- `relation_id`；

回查 execution graph，确认：

- 对应哪一个 operation scope；
- 是 ACK 还是 data signal；
- producer/consumer rank 是谁；
- direct ordinal 或 FFts graph occurrence 是什么；
- 是否只有 partial/none semantic；
- 控制链中是否夹有额外 event/Notify/profiling task。

### 13.3 典型诊断模式

| 现象 | 优先查看 |
|---|---|
| `wait_span_ns` 大 | 上游 payload duration、record 时刻、对端 rank |
| `remote_block_ns` 大 | producer 数据任务、传输拥塞、对端执行滞后 |
| `post_signal_ns` 大 | Notify 可见性、wait 退出、设备调度延迟 |
| `handoff_gap_ns` 大 | wait 后 stream 排队、调度空洞 |
| isolated resource 多 | stream/FFts order 证据缺失、未覆盖 task kind |
| boundary 增加 | 资源白名单缺失、控制链越界或输入不完整 |
| contraction ambiguity | execution order 出现分支，不能唯一投影 |
| Notify single 增加 | 采集缺端、relation identity 字段缺失或语义覆盖不足 |

### 13.4 当前尚不能直接给出的结论

当前单机图还不能可靠完成：

- 跨节点全局关键路径；
- 未校准时钟下的跨节点绝对延迟比较；
- FFts graph 内部任意两个不同 logical stream subtask 的真实硬件依赖；
- payload 数据血缘关系；当前只保留 payload 事件语义，不作为独立因果边；
- 自动判断所有 profiler-only task 是否可忽略。

这些问题不能通过增加时间最近 heuristic 解决，而需要新的事实字段或独立校准 artifact。

## 14. 当前实现边界与后续优先方向

1. **修正派生边证据传播**：建立 `exact > observed > semantic > inferred > heuristic`
   的证据格，resource 收缩取路径最弱证据；修正 FFts/mixed resource order 的
   `kind/confidence`，并升级 graph schema。
2. **完善 FFts 内部依赖事实**：调查 msprof/FFts graph 是否能导出内部依赖或 barrier token，
   区分“声明序”与“真实硬件先后”。
3. **建立诊断分析层**：在稳定 resource artifact 上实现 critical path、top wait、
   per-rank imbalance 和等待归因报告。
4. **加入多节点时钟合同**：定义 profile run manifest、node clock calibration 和
   cross-node timing status，未校准数据保持不可比较。
5. **扩展资源覆盖矩阵**：逐类评估 AI Core compute、新 transport primitive 和未知
   profiler task kind 是否应进入 resource whitelist。
6. **固定 golden 与回归解释流程**：将 gate summary 作为 golden，任何边数、boundary、
   ambiguity 或 schema 变化必须附原因。

# Ring、Mesh 与 NHR 语义追踪测试说明

## 1. 测试目标

本文用于验收 `feat-standard-ring`、`feat-mesh` 和 `feat-NHR` 三个候选分支的生产端语义插桩。
正式验收必须在同一次 workload 中同时采集：

- HCOMM plog 中的 `[HcclTaskSemantic]` 算法语义；
- msprof consolidated `msprof_*.db` 中的物理任务和性能时间；
- 算法选择日志、构建 revision 和部署库校验值。

只开启 `HCCL_STEP_TRACE=1`、但不启动 msprof 的运行只能证明通信计算正确，不能用于判断 FFTS
语义覆盖是否成功。FFTS graph task callback 由 msprof addition-info 订阅控制。

## 2. 分支与构建

| 分支 | 当前 head | 验收对象 |
|---|---|---|
| `feat-standard-ring` | `5b43135` | Standard Ring ReduceScatter/AllGather |
| `feat-mesh` | `d870111` | normal/atomic Mesh RS/AG、Mesh Direct |
| `feat-NHR` | `a00ddb6` | 普通 NHR RS/AG、NHR-Oneshot Reduce/Broadcast |

每个分支分别构建并部署 HCOMM：

```bash
git switch <branch>
git rev-parse HEAD
cd hcomm
bash build.sh --pkg
```

记录构建命令、HCOMM/HCCL revision、动态库 SHA256、`LD_LIBRARY_PATH`、设备型号、运行时
`DevType` 和测试命令。确认运行时加载的是本次构建的 `libhcomm.so`。

## 3. 采集前置条件

清理或更换 plog 与 msprof 输出目录，避免混入旧进程数据。用 msprof 包裹 workload，并确保
trace 环境变量传入被测进程：

```bash
export HCCL_STEP_TRACE=1
export HCCL_TASK_SEMANTIC_TRACE=1

msprof \
  --application="<allreduce workload command>" \
  --output="<new msprof output directory>"
```

采集完成后，必须先检查 plog 中存在以下证据：

```bash
rg "MsprofCtrlCallback called, type: 0" <plog-dir>
rg "StartAddtionInfoSubscribe:\[0\]" <plog-dir>
rg "DrvFftsProfileStart" <plog-dir>
```

这里 `StartAddtionInfoSubscribe:[0]` 中的 `0` 是成功返回码。缺少 addition-info 订阅证据时，
本轮标记为“测试环境无效”，不得把 0 条语义归因于算法插桩。

## 4. 算法选路门禁

语义统计前必须从选择日志确认真实 executor/template，不能从目录名或环境变量反推。

| 算法 | 必须确认的选路 | 预期语义 |
|---|---|---|
| Standard Ring | `ReduceScatterRing`、`AllGatherRing` | `algorithm=ring`；RS/AG step 为 `0..rank_size-2` |
| Mesh Atomic | Atomic Mesh RS/AG 模板 | `algorithm=mesh_atomic`；所有 step 为 0 |
| Mesh Normal | normal Mesh RS/AG 模板 | `algorithm=mesh`；所有 step 为 0 |
| Mesh Direct | `TEMPLATE_ALL_REDUCE_MESH_DIRECT` | `algorithm=mesh_direct`；所有 step 为 0 |
| NHR Oneshot | `AllReduceComm` 和 `TEMPLATE_ALL_REDUCE_NHR_ONESHOT` | `algorithm=nhr_oneshot`；8 rank step 为 0、1、2 |
| NHR Normal | `AllReduceComm` 和 `TEMPLATE_ALL_REDUCE_NHR` | `algorithm=nhr`；8 rank step 为 0、1、2 |

NHR 建议显式设置 `HCCL_ALGO=level0:ring;level1:NHR`。总字节数 `<=256 KiB` 用于 Oneshot，
总字节数 `>256 KiB` 用于普通 NHR；配置存在但没有进入 `AllReduceComm` 时，本轮不构成 NHR 验收。

如需临时修改 selector 才能到达目标模板，应保存补丁、选择日志和 workload 参数。该结果只用于
模板功能验证；撤销强制选择后仍需补充真实 selector 设备用例。

## 5. 合并与校验

从同一次采集取得 plog 目录和 consolidated DB 目录后执行：

```bash
cd <hccl-trace>

bash test/run_step_trace_function_test.sh \
  --out-dir test/out/<algorithm>/function \
  --plog-dir <plog-dir> \
  --msprof-db-dir <msprof-output-dir> \
  --node-id node0 \
  --min-match-rate 95
```

最低通过标准：

- 脚本退出码为 0，目标 `algorithm` 和 `phase` 的 `semantic_total > 0`；
- `exact_match_rate_percent >= 95`；当前工具只接受 exact，禁止 heuristic/时间最近补配；
- `duplicate_semantic_rows == 0` 且 `duplicate_profiler_rows == 0`；
- graph task 语义具有有效 `ffts_ctx_id`，task kind 与 msprof 物理任务类型一致；
- Ring 的 step/peer/slice 满足环轮次，Mesh 的 step 全为 0，NHR 的 peer 与当前 hop 一致；
- 保存 `merged.csv`、`summary.csv`、`validate.log`、选择日志和原始 plog/DB。

## 6. 失败判定顺序

1. 没有 `StartAddtionInfoSubscribe:[0]`：测试环境无效，重新通过 msprof 采集。
2. 没有命中目标 executor/template：算法选路未覆盖，不评价插桩正确性。
3. 已订阅 addition-info 且命中目标模板，但目标语义为 0：生产端插桩或 callback 链路缺陷。
4. 语义非空但匹配率低：检查 plog/DB 是否同次采集、device/stream/task/context 身份和 one-shot 对齐。
5. 匹配率达标但算法字段错误：按对应 Ring、Mesh 或 NHR 语义合同修复。

`test/out/old_backup` 是 msprof 已开启时的 concurrent-direct Ring 参考：其中
`reduce_scatter_direct` 具有有效 FFTS context，`allgather_direct` 走普通 task 路径。它可以证明
采集链路工作，但不能替代三个新算法分支各自的 selector 和 device golden。

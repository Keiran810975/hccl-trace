# 从克隆代码到训练诊断结果

适用版本：本仓库`nf`源码；流程核对日期2026-11-05。
本文面向要在自己的Ascend设备、容器和训练任务上采集的用户，不依赖本项目现场的机器名、卡号或数据。

## 1. 先理解需要准备什么

完整链路为：

```text
配套Host/Device通信库 + 原训练任务 + 公开调用观测
                  -> 语义plog + 完整msprof PROF目录 + calls日志
                  -> CPU离线精确关联、构图、比较、溯源
                  -> execution.html / root_causes.json / propagation.html
```

| 组件 | 在哪里运行 | 要求 |
| --- | --- | --- |
| 训练及采集 | Linux Ascend机器 | 驱动/CANN/框架兼容、授权设备、msprof、配套通信库 |
| `hccl_trace.Trace` | 每个训练进程 | 显式节点/全局Rank/实际设备ID、真实通信成员及调用位置 |
| `hccl-diag analyze` | 有足够内存/磁盘的CPU机器 | Python >=3.9，生产分析只使用标准库，无需NPU/CANN/PyTorch |
| HTML查看 | 普通浏览器 | 两个HTML均自包含，可断网查看 |

现有真实设备证据主要来自CANN8.5.1；这不是对任意新驱动、CANN或芯片版本的兼容承诺。
consolidated DB当前支持schema `1.2.0`，未知schema会报错，不能改版本字符串强行通过。
模型可以更换，但实际选择的通信算法/引擎必须有足够语义覆盖。
普通计算任务可能出现在图中，不意味着已实现所有计算算子或外部后台任务的完整因果诊断。

先区分三个结论：训练数值通过、采集/构图通过、异常定位命中。前一项不自动证明后一项。
实际部署还需要管理员确认软件ABI、Device合法加载方式及设备分配；Python安装不负责这些步骤。

## 2. 克隆和安装Python工具

在每个训练节点及分析机器上使用同一个提交。以下二选一，不需要分别克隆子目录：

```bash
git clone --branch nf --single-branch https://github.com/Keiran810975/hccl-trace.git
# Gitee镜像可替换上面的URL： https://gitee.com/tjucyx/hccl-trace.git
cd hccl-trace
export REPO="$(pwd)"
git rev-parse HEAD
python3 -m pip install -e .
hccl-diag analyze --help
```

采集时应安装到已有、能正常训练的Python环境中，不要另建一个缺少torch/torch-npu的环境后直接运行模型。
分析机器可独立创建虚拟环境并安装，不必安装训练依赖。无安装权限时，在仓库根目录运行
`python3 -m hccl.tools.diagnosis.cli analyze ...`等价于`hccl-diag analyze ...`。
跨机器传输源码或使用可编辑安装时，也要记录本次Git提交；不要运行中途更新源码。

## 3. 准备配套Host/Device库

### 3.1 设备与基础环境检查

每个节点先确认原始训练不带诊断时能完成，并核对以下项目：

- CANN Toolkit、OPS、驱动、固件及torch/torch-npu与硬件匹配；`msprof`可用。
- 已分配设备的实际runtime/profiler ID，以及它们映射到哪些物理整卡。多芯片设备不能把芯片数当卡数。
- 目标整卡没有他人任务，HBM处于正常空闲水平；AICore=0不是空闲的充分条件。
- 容器已合法映射目标设备，权限、共享内存和网络满足原训练要求；不通过特权或改命名空间绕过分配。
- 训练端口与时钟探针端口空闲，多机接口/IP可达，输出文件系统空间充足。

以下是环境模板，按实际安装路径替换：

```bash
export CANN_ROOT=/usr/local/Ascend/ascend-toolkit/latest
source "$CANN_ROOT/set_env.sh"
npu-smi info
command -v msprof
python3 -c 'import torch, torch_npu; print(torch.__version__, torch_npu.__version__)'
export WORK="$HOME/hccl-trace-runs"
export DEPLOY="$WORK/runtime/lib64"
mkdir -p "$WORK" "$DEPLOY"
df -h "$WORK"
```

不要复制旧实验目录中的镜像名、私有IP、`runtime1/3/5/7`映射或Device哈希到新设备。
已有GPT采集有每节点几十GiB的原始和图中间数据，小示例与实际模型的空间消耗差别很大；
先短采集估计规模，再为正式采集、解压及`--keep-debug`预留空间和有界超时。

### 3.2 构建Host库

优先使用管理员交付的、与本次提交对应的配套构建。需要自行构建时，在Linux/CANN开发环境进行，
依赖及构建包安装说明见[HCOMM构建](../hcomm/docs/build.md)和[HCCL构建](../hccl/docs/build.md)。
这些底层文档中的版本下载链接和验签示例是厂商基线参考，不是允许修改共享系统的授权。

传统集合通信及语义生产端在`hcomm/`，不能只构建`hccl/`就认为生产端已部署：

```bash
cd "$REPO/hcomm"
bash build.sh --pkg -p "$CANN_ROOT"
# 只有实际使用/修改新HCCL前端架构时，还需在hccl目录构建对应前端。
cd "$REPO"
```

构建需要匹配版本的编译器、CMake、CANN开发头文件、工具链及第三方依赖。
如现场依赖不能联网下载，按构建文档准备依赖并指定路径；不能把编译未完成当作运行问题。
Host构建与Device构建必须来自同一提交和兼容配置，保留各自构建日志。

可将本次Host目标的三个库复制到自己的部署目录。下面只搜索原生构建树，拒绝缺失或多份模糊结果：

```bash
python3 - <<'PY'
import os, shutil
from pathlib import Path
repo, target = Path(os.environ['REPO']), Path(os.environ['DEPLOY'])
for name in ('libhcomm.so', 'libhccl_alg.so', 'libhccl_plf.so'):
    paths = [p for p in (repo / 'hcomm/build').rglob(name)
             if p.is_file() and not p.is_symlink() and '_CPack_Packages' not in p.parts]
    if len(paths) != 1:
        raise RuntimeError('Check actual build output for ' + name + ': ' + repr(paths))
    shutil.copy2(paths[0], target / name)
PY
export LD_LIBRARY_PATH="$DEPLOY:${LD_LIBRARY_PATH:-}"
ldd "$DEPLOY/libhcomm.so"
sha256sum "$DEPLOY/libhcomm.so" "$DEPLOY/libhccl_alg.so" "$DEPLOY/libhccl_plf.so"
```

`libhccl.so`、RDMA及其他运行依赖仍须来自同一兼容部署，不要将其他机器的一批`.so`随意拼入。
检查训练日志及自己进程的`/proc/PID/maps`，确认实际加载本次部署库；只设置环境变量不算加载证据。
已有私有CANN安装可采用配套`.run`包安装方式，但须先查看其`--help`并确认真实目标路径和恢复方法。
不要为了采集覆盖宿主共享CANN或升级共享驱动。

### 3.3 AI_CPU路径还需要Device包

当原训练走AI_CPU时，Host侧打点不覆盖设备内部的细粒度通信任务。
必须构建并合法加载配套`aicpu_hcomm.tar.gz`；官方包通常不能产生本分支新增的Device语义。
不要为了避开Device部署而把原训练强制改成另一个执行引擎或修改算法选路源码。

Device产品配置与芯片/SDK有关。`hcomm/build.sh --pkg --full`提供全量打包路径，
但脚本内有产品默认值；在新型号上应由管理员确认配置，不能盲目照搬。
已确认Device产品配置后，也可只构建所需的AI_CPU包，使用与Host相同的依赖配置，例如：

```bash
# DEVICE_PRODUCT必须由当前芯片和配套CANN构建配置确认，不从Rank或镜像名猜。
: "${DEVICE_PRODUCT:?Set the verified Device PRODUCT for this SDK}"
cmake -S "$REPO/hcomm" -B "$REPO/hcomm/build_device" \
  -DCUSTOM_ASCEND_CANN_PACKAGE_PATH="$CANN_ROOT" \
  -DCANN_3RD_LIB_PATH="$REPO/hcomm/third_party" \
  -DCANN_UTILS_LIB_PATH="$REPO/hcomm/utils" \
  -DDEVICE_MODE=ON -DKERNEL_MODE=ON -DPRODUCT_SIDE=device \
  -DPRODUCT="$DEVICE_PRODUCT" -DUSE_ALOG=0 -DCMAKE_BUILD_TYPE=Release
cmake --build "$REPO/hcomm/build_device" --target generate_device_aicpu_package -j8
sha256sum "$REPO/hcomm/build_device/aicpu_hcomm.tar.gz"
```

这只是构建，不是签名或部署。优先由管理员提供可信签名与加载路径。
开发包若需临时设备验签调整，必须先得到明确授权，核验整卡两芯片空闲，保存各卡真实原值和
私有CANN内原Device包，设置独立于训练进程的定时回滚并演练，之后才允许生效。
采集成功、失败或中断，都要在离线分析前恢复原包/策略、实读核验，再撤销回滚保护。
普通shell的`trap`不能替代独立恢复器，原值也不固定为旧实验的False/5。

现场常见包位置为`CANN_ROOT/opp/built-in/op_impl/aicpu/kernel/aicpu_hcomm.tar.gz`，
但真实路径应从本机安装与加载证据确认；只在自己的私有运行时操作，不能替换共享挂载包。
没有合法加载权限就停在这里联系管理员，不以降低语义门禁、绕开验签或只生成HTML代替部署成功。
仓库内`node03_device_guard.py`有现场授权路径和设备白名单，不能作为通用新机器恢复器直接执行。

## 4. 先跑一个最小端到端采集

此示例不下载模型、不注入异常，只做真实AllReduce及数值检查，证明环境和采集链路可用。
假设已核验授权设备的runtime/profiler ID为`1,3`，且对应两张已分配的整卡；不同映射必须改下面的值。
不要直接把`LOCAL_RANK`当设备ID，避免额外设置可见设备变量后又混用旧编号。

在原训练Python环境、仓库根目录运行：

```bash
cd "$REPO"
export RUN_ID="smoke-$(date -u +%Y%m%dT%H%M%SZ)"
export NODE_ID=nodeA
export CAPTURE="$WORK/captures/$RUN_ID"
export NODE_CAPTURE="$CAPTURE/nodes/$NODE_ID"
export DEVICES=1,3
mkdir -p "$NODE_CAPTURE/plog" "$NODE_CAPTURE/calls"
export HCCL_STEP_TRACE=1
export ASCEND_GLOBAL_LOG_LEVEL=1 ASCEND_SLOG_PRINT_TO_STDOUT=0
export HCCL_TRACE_RUN_ID="$RUN_ID" HCCL_TRACE_NODE_ID="$NODE_ID"
export HCCL_TRACE_CALLS_DIR="$NODE_CAPTURE/calls"
export ASCEND_PROCESS_LOG_PATH="$NODE_CAPTURE/plog"
msprof --application="python3 -m torch.distributed.run --standalone --nproc-per-node=2 --max-restarts=0 $REPO/examples/diagnosis_collectives.py --devices $DEVICES --warmup 2 --iterations 8 --size-mib 2 --numerics-dir $WORK/numerics/$RUN_ID" \
  --output="$NODE_CAPTURE/msprof" --hccl=on --task-time=on --type=db
```

`msprof --application`中的路径示例不含空格；若自己的路径含空格，需要对application内部参数再次正确引用。
采集会继承已经配置的`LD_LIBRARY_PATH`和原训练执行引擎；不要同时套另一层profiler。
本示例原本就有逐调用设备同步以检查数值，这不是建议给实际模型的每个调用新增同步。

采集后检查：

```bash
find "$NODE_CAPTURE/msprof" -name 'msprof_*.db'
rg '\[HcclTaskSemantic\]' "$NODE_CAPTURE/plog" -m 1
python3 - <<'PY'
import json, os
from pathlib import Path
paths = sorted((Path(os.environ['WORK']) / 'numerics' / os.environ['RUN_ID']).glob('rank-*.json'))
rows = [json.loads(p.read_text()) for p in paths]
assert len(rows) == 2 and {r['user_rank'] for r in rows} == {0, 1}
assert all(r['status'] == 'passed' and len(r['results']) == 10 for r in rows)
print('Both ranks completed 2 warmup + 8 measured iterations; numerics passed')
PY
```

预期每个前台设备有唯一一份consolidated DB、每个Rank有calls日志和完整数值结果。
DB存在不等于调用绑定正确，plog有记录不等于所有任务已精确关联；最终由离线门禁核验。
msprof返回0也不能替代全部Rank实际结束和数值通过。

## 5. 拿到第一份诊断报告

可以直接在设备机器CPU上分析，也可以将完整capture传到另一台CPU机器。
输出必须是不存在的新目录，且位于输入目录之外：

```bash
hccl-diag analyze --capture "$CAPTURE" --mode rolling \
  --output "$WORK/results/$RUN_ID" --keep-debug
```

最终目录只有：

```text
results/RUN_ID/
  execution.html
  root_causes.json
  propagation.html
results/RUN_ID.debug/          # --keep-debug保留的完整中间分析，单独目录
```

正常小负载不要求一定出现根因候选。命令返回0只表示流水线通过，还要看JSON状态和覆盖率。
第一次使用保留debug，便于判断绑定、图、参考比较和评分在哪一层出问题。
未指定`--keep-debug`时本次临时分析在退出后清理，但原始capture不会被此CLI删除。

## 6. 换成自己的训练任务

### 6.1 为每次真实通信记录公开位置

保留原始训练、分布式启动、通信域和数值语义。接入SDK后，把上面application替换为自己的本节点启动命令。
下面是显式AllReduce接入骨架，`tensor`必须是实际FP32通信输入，其他类型要改对应dtype：

```python
from hccl_trace import Trace

# 实际设备ID应来自已经核验的本节点映射；dp_group为真实训练通信域。
with Trace.from_environment(device_id=actual_profiler_device_id) as trace:
    trace.group("dp", dist.get_process_group_ranks(dp_group))
    for stage, count in (("warmup", warmup_steps), ("measured", measured_steps)):
        for iteration in range(count):
            with trace.iteration(iteration, stage=stage):
                # 原有计算，不添加用于打点的设备操作。
                with trace.collective(
                    group="dp", call_site="layer3.gradient",
                    operation_type="AllReduce", element_count=tensor.numel(),
                    dtype="float32", reduction="sum",
                ):
                    dist.all_reduce(tensor, group=dp_group)
                existing_verified_device_completion_boundary()
                trace.completion_boundary()
```

`existing_verified_device_completion_boundary()`是要替换的适配点，不是SDK提供的函数。
它必须对应原训练本来已有、已证明设备完成的边界；SDK只记录这个事实，本身不执行同步。
可以在原本一个完成边界后一次确认多个pending调用，不要求逐collective同步。
Python API返回和仅安排流依赖的`Work.wait()`不能直接当成CPU观测到设备完成；
缺少可验证完成边界或多个异步调用无法唯一绑定时，应补框架适配，不能靠最近时间/序号猜配。

- 同一个位置使用稳定的`group/call_site`，每轮同位置的重复调用由`occurrence`区分。
- 各通信域注册实际成员，不用整个world替代子通信域；多通信域歧义可提供真实`db_group_name`。
- `element_count`是对应HCCL API的实际count语义，不是字节数；AllGather/ReduceScatter不能不核对就套同一公式。
- 预热明确标为`warmup`，正式标为`measured`，两个阶段可各自从0计数；参与Rank必须对位置和通信结构达成一致。
- 同一Trace不支持跨线程并发提交；需要线程/框架适配，不能伪造全局调用顺序。
- 如需诊断Host准备迟到，可用`time.clock_gettime_ns(time.CLOCK_MONOTONIC_RAW)`在真实准备开始处取样，
  通过`preparation_start_raw_ns=`传入collective；不能拿注入真值当公开准备起点。

### 6.2 DDP/FSDP与其他内部通信

只包住`loss.backward()`、训练step或整个模型，不能自动标识其中每次梯度通信。
应在框架实际通信Hook/通信适配层记录：真实group、桶或调用的稳定身份、类型/count/dtype和提交包络，
并在原本已有的真实完成边界统一确认。不要改变原Hook的Future返回、归约/平均规则或重叠行为。
模型初始化Broadcast、参数同步、barrier等也需要记录或独立证明其辅助通信身份，不可与梯度调用混配。

`test/gpt2_train.py`展示了本项目GPT/DDP的适配及精确buffer证据，但不是任意模型的通用启动器。
采集元数据支持显式`sdk_auxiliary_operation_types`，只允许列入已确认的辅助操作，
例如确实存在且可唯一绑定的初始化Broadcast；不能靠宽泛白名单忽略不明业务通信。
如果自己的框架没有可用适配点，目前需要接入工作，而不是只换一个训练命令就保证成功。

## 7. 选择比较模式和诊断策略

### Rolling：与同次采集前5个正式轮比较

```bash
hccl-diag analyze --capture "$CAPTURE" --mode rolling \
  --output "$WORK/results/$RUN_ID-rolling" --keep-debug
```

需要SDK或独立核验的iteration-map。至少保留连续5个正式轮作为参考，第6个正式轮起才可能比较；
不能把预热混入历史。正式轮次更多有利于覆盖不同位置，但持续异常也可能污染滚动参考。
动态结构、缺失位置或历史不足会保留为`not_comparable`/`insufficient_history`，不等于健康。

### Baseline：与独立正常运行比较

先用相同模型、输入形状、Rank、通信域、软件、设备和算法配置采集正常组，再采集待测组；
两个采集使用不同RUN_ID和新目录。没有合适的正常参考不要伪造一份。

```bash
hccl-diag analyze --capture /path/to/captures/abnormal \
  --mode baseline --baseline /path/to/captures/normal \
  --output /path/to/results/abnormal-baseline --keep-debug
```

Baseline不强制训练SDK，但仍需独立证明节点/设备及通信实例绑定；无SDK不等于无需适配。
两次均有SDK时，公开位置、实际成员和collective形状必须一致。
Baseline的规则与Rolling不同；当前Baseline主要覆盖设备执行慢化，不是Host准备迟到溯源的替代路径。

### 显式选择实验策略

| 参数 | 含义 |
| --- | --- |
| 不传或`--source-policy legacy` | 默认兼容策略，内部候选与外部线索分开 |
| `--source-policy dual` | 执行局部Top1提案与有证据的Host迟到提案比较，现有单机实验使用 |
| `--source-policy dual-v2` | 多机源头排序试验，协议等待只作线索，现有多机实验使用 |

dual/dual-v2只适用于Rolling，不能同时指定独立candidate过滤策略。
它们是启发式相对选择，不是已校准的故障报警器，存在正常误报和独立位置漏诊。
复现某次实验要显式记录策略，不能将默认legacy的结果当作dual-v2结果。

```bash
hccl-diag analyze --capture "$CAPTURE" --mode rolling --source-policy dual \
  --output "$WORK/results/$RUN_ID-dual" --selected-iteration-view --keep-debug
```

`--selected-iteration-view`只缩小最终执行图，不缩小诊断输入；显示候选所在正式轮，
没有候选时显示最后正式轮。该HTML不是全部轮次；全量图在保留的debug中，原始数据仍在capture中。

## 8. 多机采集：每节点独立输出，统一绑定

以两节点nodeA/nodeB、每机2Rank为例。两端提交、库哈希、共享RUN_ID相同，
`NODE_ID`、实际设备映射和`--node-rank`不同；全局Rank由原launcher产生，不手动伪造。
沿用已经跑通的分布式IP/接口、端口和设备配置；本例不自动SSH部署或停止任何任务。

每端先按第4节设置采集环境，其中RUN_ID由操作者统一指定，而不是各机独立取当前时间：

```bash
export RUN_ID=my-training-001
export NODE_ID=nodeA           # 另一台为nodeB
export CAPTURE="$WORK/captures/$RUN_ID"
export NODE_CAPTURE="$CAPTURE/nodes/$NODE_ID"
export HCCL_TRACE_RUN_ID="$RUN_ID" HCCL_TRACE_NODE_ID="$NODE_ID"
export HCCL_TRACE_CALLS_DIR="$NODE_CAPTURE/calls"
export ASCEND_PROCESS_LOG_PATH="$NODE_CAPTURE/plog"
mkdir -p "$NODE_CAPTURE/calls" "$NODE_CAPTURE/plog"
```

把本节点原启动命令交给msprof。例如nodeA如下，nodeB改`--node-rank=1`和本节点设备列表：

```bash
export MASTER_ADDR=192.0.2.10  # 文档示例地址，必须换为两机可达的真实训练地址
msprof --application="python3 -m torch.distributed.run --nnodes=2 --nproc-per-node=2 --node-rank=0 --master-addr=$MASTER_ADDR --master-port=29500 --max-restarts=0 $REPO/examples/diagnosis_collectives.py --devices $DEVICES --warmup 2 --iterations 8 --size-mib 2 --numerics-dir $WORK/numerics/$RUN_ID" \
  --output="$NODE_CAPTURE/msprof" --hccl=on --task-time=on --type=db
```

`DEVICES`在每端按本机映射设置；原训练若需要HCCL接口/IP变量，保留已验证的原配置。
若需要跨机时间对齐，必须在执行上面采集之前完成下一节的before探针。

### 8.1 可选但需预先安排的时钟探针

没有探针仍可分析跨机拓扑和本地时长，但不允许据此相减跨机绝对时间。
要使用`--require-clock-alignment`，按以下顺序执行，不能训练后再补before探针：

1. 在nodeA单独终端启动参考服务，等待打印ready。使用仅授权节点可访问的内网地址与独立空闲端口。
2. nodeB完成before探针；更多节点各自完成。所有before完成后，才同时启动各节点msprof/训练。
3. 等待所有节点的训练和msprof都完整退出，再由nodeB执行after；更多节点也各自after。
4. 参考服务收到所有after后正常退出并写文件。超时或漏节点时不拿不完整证据宣称校时通过。

nodeA独立终端：

```bash
python3 test/multinode_clock_probe.py serve --address "$MASTER_ADDR" --port 29860 \
  --capture-id "$RUN_ID" --node-id nodeA --reference-node nodeA --peers nodeB \
  --timeout 7200 --output "$CAPTURE/nodes/nodeA/clock.json"
```

nodeB在采集前和所有节点采集结束后分别执行：

```bash
python3 test/multinode_clock_probe.py probe --address "$MASTER_ADDR" --port 29860 \
  --capture-id "$RUN_ID" --node-id nodeB --reference-node nodeA --phase before \
  --timeout 60 --output "$CAPTURE/nodes/nodeB/clock-before.json"
# 所有节点采集完整结束之后，才执行下一条。
python3 test/multinode_clock_probe.py probe --address "$MASTER_ADDR" --port 29860 \
  --capture-id "$RUN_ID" --node-id nodeB --reference-node nodeA --phase after \
  --timeout 60 --output "$CAPTURE/nodes/nodeB/clock-after.json"
```

需要在nodeB同样设置真实`MASTER_ADDR`和共享`RUN_ID`。不要把探针端口公开到不可信网络。
更多节点将服务的`--peers`设为逗号分隔的实际节点名，分别保存独立before/after文件。
这是CPU软件探测，不改系统时间，不是硬件PTP，也不是逐笔RDMA硬件完成计时。

### 8.2 汇集目录和采集清单

把各节点自己的整个节点目录传到分析机同一capture下，不要重命名内部PROF目录或只挑部分DB。
可用rsync/scp/tar等原有安全通道，保留相对目录，传输后核验文件SHA256；不要删除原文件。

```text
my-training-001/
  capture.json
  nodes/nodeA/plog/
  nodes/nodeA/msprof/PROF_.../     # DB、host/start_info/end_info、device_*/sqlite等完整保留
  nodes/nodeA/calls/rank-0.jsonl
  nodes/nodeA/calls/rank-1.jsonl
  nodes/nodeA/clock.json
  nodes/nodeB/plog/
  nodes/nodeB/msprof/PROF_.../
  nodes/nodeB/calls/rank-2.jsonl
  nodes/nodeB/calls/rank-3.jsonl
  nodes/nodeB/clock-before.json
  nodes/nodeB/clock-after.json
```

在采集根创建`capture.json`，将clock文件关联到节点；以下路径相对此JSON所在目录：

```json
{
  "run_id": "my-training-001",
  "nodes": [
    {"node_id": "nodeA", "clock_probe_files": ["nodes/nodeA/clock.json"]},
    {"node_id": "nodeB", "clock_probe_files": ["nodes/nodeB/clock-before.json", "nodes/nodeB/clock-after.json"]}
  ]
}
```

节点/Rank/device由SDK运行身份与真实DB交叉核对，不由目录名推测。无SDK时可提供runtime/topology或旧manifest，
但仍需独立证明共享operation、所有通信成员及正式轮次；仅给机器数和卡数不够。
不要在同一设备目录混入后台采集或两次运行的DB，分析器不会猜哪一份是前台。

完成汇集后：

```bash
hccl-diag analyze --capture /path/to/my-training-001 --mode rolling \
  --source-policy dual-v2 --require-clock-alignment \
  --output /path/to/results/my-training-001 --selected-iteration-view --keep-debug
```

默认校时误差容限1ms，前后探针必须覆盖每份实际profiler会话，并与本次capture一致。
失败先检查时间证据；不能以首个AllReduce对齐、修改原时间或扩大预算来制造通过。
无校时时不传`--require-clock-alignment`，只解释本地时长/拓扑。
`--allow-uncalibrated-clock`是显式保留本地时间轴的降级选项，不能与require同时使用，
也不能把降级结果宣称为已经校时。

## 9. 查看、验收和保留结果

`execution.html`显示真实任务与已有依赖，`propagation.html`展开已报告的证据路径；
在浏览器打开即可，不需要服务端。大图可能较大，可用所选轮切片减小最终HTML。
JSON是统计入口，不用浏览器截图替代数值检查：

```bash
python3 - /path/to/results/RUN_ID/root_causes.json <<'PY'
import json, sys
from pathlib import Path
r = json.loads(Path(sys.argv[1]).read_text())
for k in ('run_id', 'status', 'diagnosis_status', 'mode', 'primary_candidate_id', 'primary_source_id'):
    print(k, r.get(k))
print('communication candidates', len(r.get('communication_source_candidates', r.get('candidates', []))))
print('external clues', len(r.get('external_anomaly_clues', [])))
print('unresolved observations', len(r.get('unresolved_observations', [])))
print('quality', r.get('quality'))
print('coverage', r.get('coverage'))
PY
```

退出码含义：0为流水线通过；2为参数/输入/绑定；3为语义关联；4为图或诊断；5为报告发布。
语义缺失、重复设备或歧义绑定必须修输入/部署，不通过降匹配率、最近时间关联或补造依赖绕过。

解释结果时注意：

- `communication_source_candidates`是通信内部候选，`external_anomaly_clues`包括Host线索，
  `unresolved_observations`是尚未归因事实；dual策略另有`source_candidates`及`primary_source_id`。
- 候选不是已确认的物理故障；没有候选不证明正常。相对Top1可能选到其他轮次或Rank的真实波动。
- 传播只展示有证据的路径，0条链不等于证明没有传播，也不允许据此补箭头。
- Host区间与设备task分单位；Notify等待和RDMA提交不冒充纯网络传输时间或硬件完成时间。
- 软件校时只支持其精度范围内的解释，不提供精确全局workload关键路径。

每次至少保留：源码提交、配置/启动命令、各Host/Device库哈希、软件版本、实际设备映射、
全部Rank数值结果、完整plog/PROF/calls/clock、三报告、需要的debug，以及恢复实读凭证。
原始数据如果经过自己的留档流程删除，必须先逐文件验SHA并确认可恢复；只有三报告不能完整重建原采集。
不要清理共享日志目录，不覆盖旧运行目录；新运行和新分析都换新ID/输出目录。

## 10. 常见卡点

| 现象 | 优先检查 |
| --- | --- |
| 训练不带诊断也失败 | 先修基础框架、设备权限、通信网络和数值；暂不进入诊断 |
| msprof有DB但语义为0 | 是否实际加载新Host；AI_CPU是否加载配套Device；trace/log级别及算法覆盖 |
| 出现旧JSON/CSV输入报错 | 保留并传入consolidated DB，不用task_time.csv替代 |
| 缺少/重复device DB | 是否混了后台或多次采集、是否收齐所有节点，实际映射是否正确 |
| SDK缺completion或API绑定歧义 | 真实完成边界、dtype/count/group、内部通信Hook、异步包络及原host/start_info |
| Rolling缺历史 | 至少前5正式轮同位置同结构，预热不计；动态结构不可硬配 |
| 多机operation未绑定 | 全局Rank和通信域成员是否完整；相同DB算子名不是跨机共享身份 |
| 校时缺失/误差过大 | before/after顺序、共享capture ID、探针覆盖、端口、PROF原始时钟元数据 |
| 报告目录已存在 | 换新的输出目录，不覆盖旧证据 |
| 内存/磁盘不足 | 缩短首次采集，保留原输入；切片只减最终图，不消除全量分析开销 |
| 进程中断 | 只取消自己的本次任务；先恢复包/策略/网络并实读，再撤独立timer，不无界重试 |

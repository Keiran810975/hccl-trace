# 910C 双机 8 Rank Workload 与异常注入设计

日期：2026-10-24。状态：设计提案，尚未适配执行器、分配设备或启动实验。
此前 Node0+Node2 自动监控已按用户要求取消，本方案不会恢复监控。

## 1. 验证目标

在同一套正常负载上分别注入单个异常，检查诊断能否区分慢化源头和被动等待者，
并通过真实依赖解释影响如何从一个 Rank 传播到同机、另一机的相关 Rank。
这是工程功能与探索性效果验证，不直接宣称诊断准确率已达到某个百分比。

主要判断：与对应 baseline 比较，报告变化的任务或本地空隙、源头候选、
实际受影响的 Wait 及证据路径。不能把最长 Wait 直接当作根因，
也不能只凭任务变慢断言网络、SDMA 或计算单元是唯一物理原因。

## 2. 拓扑与设备

建议继续使用物理 Node0 和 Node2，自有非特权容器均为 `zjy-new`：

| 物理节点 | torchrun node-rank | 全局 Rank | 每机建议容器 runtime 设备 |
|---|---:|---|---|
| Node0 / 192.169.0.173 | 0 | 0、1、2、3 | 1、3、5、7 |
| Node2 / 192.169.0.125 | 1 | 4、5、6、7 | 1、3、5、7 |

按此前映射，runtime1/3/5/7 对应物理9/11/13/15，即 NPU4/5/6/7 的 chip1。
这只是候选分配，运行前必须重新核实，不代表资源已预留。
一个 Rank 对应一个 runtime 设备；本方案特意从四张不同整卡各选一颗芯片，
便于隔离目标卡资源竞争，而不是把四个 Rank 放在同两张卡的两个芯片上。

运行与验签以整卡为资源边界，需要核对两机目标整卡均空闲。
过去的临时验签授权仅覆盖两机 NPU7，**不自动扩展到 NPU4-6**；
若仍需调整验签才能加载配套 Device，实际执行前须获得新增整卡范围的授权。
不修改设备共享策略、他人容器或宿主公共 CANN。

## 3. 主 Workload

保持已有双机 4 Rank 测试的每 Rank 负载不变，只将总 Rank 数增加到8：

| 项目 | 建议配置 |
|---|---|
| 计算/通信形式 | Transformer 形状的合成 BF16 GEMM/GELU + FP32 SUM AllReduce |
| 计算尺寸 | tokens=2048，hidden=8192，FFN=32768 |
| 每轮 Block 数 | 8 |
| 每 Block | 4次 GEMM/GELU，穿插3次 AllReduce |
| 三个通信桶 | 128、256、512 MiB，每个 Rank 同样大小 |
| 每轮业务 AllReduce | 24次，所有8 Rank参加同一前台通信域 |
| 每 Rank 每轮输入 | 8 x (128+256+512) = 7168 MiB = 7 GiB |
| 全8 Rank每轮输入之和 | 56 GiB，不是网络实际收发量 |
| 正式轮数 | 10轮预热 + 50轮测量 |
| 每次完整运行 | 1440次业务 AllReduce；不乘 Rank 数重复计数 |
| 每 Rank 测量期输入 | 350 GiB |
| 正确性 | 检查8 Rank的最终桶SUM结果、正常完成与退出；记录 max_error |

这不是完整 Transformer 训练，没有真实 attention、反向传播或优化器。
每 Rank BF16 权重约14 GiB，通信桶共896 MiB；激活、运行时、缓存及竞争负载另计，
需要预检测量峰值显存，不能按静态估算直接启动。

每个 Block 的逻辑顺序为：

```text
GEMM/GELU -> AllReduce(128 MiB)
GEMM/GELU -> AllReduce(256 MiB)
两次 GEMM/GELU -> AllReduce(512 MiB)
```

不预先宣称全部采用 flat Ring。记录真实 HCCL executor、算法、通信域及 transport，
baseline 和异常组必须保持同一配置；算法/任务结构变化时不得强行配对。
配置摘要 AllReduce、barrier、预热和后台通信不计入上述业务次数，且应分别识别。

## 4. 异常位置与强度

统一测试位置为 **Node2 / Rank4 / measured iteration25 / block3 / bucket1**，
全部为0基编号，即第26个测量轮、第4个 Block 的256 MiB AllReduce。
位置位于测量区间中部，便于保留异常前后的上下文与恢复区间。

| 类型 | 注入方法与三档强度 | 持续范围 | 应检查的诊断证据 |
|---|---|---|---|
| 调用前晚到 | Rank4在指定 AllReduce 前 sleep 1/20/200 ms | 指定调用一次 | 对端等待是否增加；是否有独立提交证据支持Rank4该次调用晚到 |
| 数据搬运竞争 | Rank4芯片上并发1/2/4个后台D2D Copy进程，每进程两个256 MiB缓冲区 | iteration25-29 | 哪些前台Copy/Reduce任务变化，实际依赖的下游Wait是否增加 |
| 通信与计算竞争 | Rank4芯片上并发1/2/4个后台BF16 4096x4096 GEMM进程 | iteration25-29 | 前台任务执行或排队是否变化，变化是否沿真实依赖传播 |
| 跨节点通信竞争 | Rank4与Rank0芯片间并发1/2/4组后台256 MiB FP32 AllReduce，独立通信域和端口 | iteration25-29 | 前台跨机通信相关任务、Wait的变化及真实共享路径证据 |
| 网卡带宽受限 | 计划设置75%/50%/25%的带宽上限 | 单独样例 | 仅在可验证RoCE限速接口具备后执行，目前保留blocked |

每次只注入一种异常。背景窗口为上述5个轮次，不是只作用于指定256 MiB调用；
该区间内所有Block/桶都可能受影响，不能把窗口开始后的第一个长Wait当作指定根因task。
正常组使用同样的控制barrier和测量流程，避免把新增同步解释为异常传播。

D2D Copy可能同时竞争SDMA/HBM；GEMM也可能竞争HBM和调度资源；
后台AllReduce同时占用本地与网络资源。未经计数器和执行证据确认，不分别称为纯SDMA、
纯计算单元竞争或纯RoCE网络拥塞。并发数量也不保证与慢化幅度线性对应。

调用前sleep不等于HCCL内部phase/step/event延迟。现有AI_CPU库未验证内部task注入，
不把Host注入接口存在当作Device端支持。若仅观察到长Wait而缺少上游晚到证据，
必须报告上游未定位，不能用私有注入日志替诊断工具填写Rank4根因。

## 5. 运行顺序和样例数

1. 先做2机8Rank小消息正常测试，验证8个设备映射、数值、语义、精确合并和跨机依赖。
2. 再用主计算尺寸和主桶大小跑1轮预热+2轮测量的正常采集预检，核对显存、采集量和图门禁。
3. 跑10+50轮正常baseline，完整诊断通过后，先各选一档验证四类异常，优先级为20ms晚到、
   Copy竞争2、计算竞争2、通信竞争2。连同baseline共5次完整运行。
4. 功能链路和注入效果明确后，再覆盖四类异常的三档强度：1个baseline+12个异常=13组配置。
5. 采用3个独立重复，每个重复单独采baseline，合计39次运行；不能把50个iteration或8个Rank
   当成50份或8份独立故障样本。可额外在每组末尾复跑正常组，检查环境漂移。

首次只固定一种通信规模和一个注入位置，不同时铺开数据量、位置和算法矩阵。
后续需要扩展时，再分别增加small的32/64/128 MiB、large的256/512/1024 MiB，
以及iteration10/40或换目标Rank；每种规模要有自己的baseline。

## 6. 诊断、输出与验收

每例保留真实 msprof consolidated DB、AI_CPU语义和控制元数据，严格精确合并。
源代码快照、配套Host/Device哈希、8Rank映射、算法和前后台进程/通信域单独记录。
业务调用与DB operation的绑定须有实际日志/DB证据，不按DB总序号盲配。
对比时使用核实的相同业务调用和稳定测量区间，不能将预热冷启动混作稳定参考。

现有私有控制events含异常配置，不能直接当作诊断输入。若要进一步自动定位Host晚到，
应为所有正常/异常组统一记录中立的调用开始/返回事实，与私有注入真值隔离，
并单独实现和验证其与DB调用的关联；目前不能假设这条分析能力已具备。

预期依赖解释是：源头附近的执行/提交变化，经实际Record/Wait关系影响相关Rank。
哪些Rank、哪些phase/step受影响应由图给出，不预设所有其他7Rank都等待，
不按相邻Rank或上一step臆造边，也不跨机相减未校准时间。

每例应导出：

- `execution.html`、`waits.html`、`resource.html`，展示真实任务与依赖。
- `diagnosis.json`及本地关键路径报告，保留证据等级与未决关系。
- `comparison/report.json`、`slow_tasks.csv`、`root_causes.csv`，记录相对baseline的变化。
- `comparison/index.html`及源头附近baseline/异常同尺度对比图，提供真实边和任务详情。
- 独立验收表，将输出与注入真值比较，而不是让分析器读取真值生成结论。

建议图包括整轮上下文、源头与受影响Wait的局部图、正常/异常对照。
同尺度下baseline过短时可以另给baseline放大图，但必须注明不同缩放比例。
跨节点各用节点本地时间，图上不得暗示已建立全局统一时钟。

分三层记结果：执行是否成功、注入是否造成可观测影响、诊断是否正确定位。
注入成功但前台无明显变化记为no_effect；门禁失败、未定位、误定位、跳过和重试都保留，
不只挑有明显异常的轮次截图。根因粒度分别统计Node/Rank、业务调用和内部task，
不能把只找对Rank计为精确定位内部task；物理故障类型识别与源头候选定位也要分开。

## 7. 需要的代码适配

目前 `test/two_node_suite.py` 固定调用 `main(nnodes=2, ranks_per_node=2)`；
`test/four_node_suite.py` 的校验只接受4x4或2x2，因此本方案不是只改cluster JSON就能执行。

- 为双机入口增加每机Rank数选项，默认仍保留2；校验明确加入2x4，避免放开任意未经验证拓扑。
- 样例前缀使用独立 `2n8r`，不得与旧2n4r或4机目录冲突；默认目标改为Rank4、通信peer为Rank0。
- 每节点配置4个真实runtime设备；前后台Rank映射、正确性、输出数量与独立端口做针对性回归。
- 基线/异常报告使用同一拓扑、尺寸、算法和受控调用参考；补齐调用绑定及稳定参考范围的证据。
- 重新适配所选整卡的Device加载、独立恢复定时器和有界退出，不复用旧NPU7小负载guard冒充8Rank保护。

核心 `multinode_commmix_train.py` 已按world size执行AllReduce，现有异常控制也按
`ranks_per_node`换算节点；优先复用，不另写一套通信内核。
本次仅形成设计文档，不变更执行器，不启动服务器任务，也不扩大原验签授权。

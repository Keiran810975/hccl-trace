# HCCL-Trace讲解稿：实现原理、使用流程与注意事项

整理日期：2026-11-07。适用本仓库`nf`实现；面向了解分布式训练、但不熟悉工具内部代码的听众。
建议按下面的主线讲10～15分钟，现场配置和完整命令交给[从零开始运行训练诊断](从零开始运行训练诊断.md)。

## 一、开场：一分钟讲清它做什么

> 分布式训练变慢时，最明显的现象经常是某个Rank等待很久，但等待者不一定是源头。
> 我们的工具把三类信息结合起来：msprof记录真实设备执行，通信库打点说明算法含义，训练侧SDK说明调用位置。
> 然后在CPU上离线关联这些记录，构建有证据的依赖图，与历史正常表现比较，给出慢化源头候选和已观察到的传播路径。
> 最终用户拿到执行图、结构化结果和传播报告。它帮助缩小排查范围，不会仅凭一个长Wait就认定网络坏了或某张卡故障。

一句话总结：**不仅看“哪里慢”，还结合“它在做什么、它在等谁”，解释通信慢化。**

### 建议的讲解顺序

| 顺序 | 讲什么 | 听众需要记住的重点 |
| --- | --- | --- |
| 1，约1分钟 | 为什么需要它 | 等待最久的Rank不一定是源头。 |
| 2，约4分钟 | 三类输入、精确关联和依赖图 | 任务含义、执行时间、训练位置各有事实来源。 |
| 3，约2分钟 | 怎样判断异常 | 与可比较参考比慢化，再结合路径与源头策略；候选不是已确认故障。 |
| 4，约3分钟 | 怎样采集和分析 | 配套部署、训练接入、采集、离线诊断、看报告。 |
| 5，约2分钟 | 使用边界 | 版本、完成边界、校时、数据留存和误报漏诊。 |

## 二、实现原理：分五步解释

### 1. 三类输入，各管一件事

| 输入 | 能回答的问题 | 不能替代什么 |
| --- | --- | --- |
| msprof consolidated DB | 什么任务实际执行了？在哪条stream上？起止时间与耗时是多少？ | 不自动知道任务属于算法第几步或训练第几轮。 |
| HCOMM语义plog | 该任务属于哪个算法、phase、step、slice，以及Rank/peer和操作角色？ | 日志时间不是设备执行时长。 |
| 训练侧SDK调用记录 | 这是哪个通信域、第几轮、哪个公开调用位置、什么类型/大小的collective？ | Python调用返回不等于设备完成。 |

Node是机器，Rank是通信参与进程，Device是实际设备编号；三者不能互相推算。
训练iteration与通信算法step也不是同一层概念。

```text
在线：原训练 + 配套通信库语义打点 + msprof + 训练侧公开调用记录
                              |
                              v
               plog / msprof DB / calls.jsonl
                              |
离线（CPU）：解析 -> 精确关联 -> 依赖构图 -> 历史比较 -> 源头与路径
                              |
                              v
          execution.html / root_causes.json / propagation.html
```

可这样讲：“msprof给任务计时，通信库给任务贴算法标签，SDK把它放回训练中的位置。”

### 2. 语义标签怎样跟着异步任务走

算法执行时本来就知道phase、step、分片和对端，我们用C++作用域对象保存当前上下文。
在Copy、Reduce、Record、Wait等具体操作附近补上事件角色，并以一次性标签绑定相应任务。

关键是**在TaskData创建时保存快照**，以后上报读任务自己的标签，不读已经变化的线程上下文。
否则任务A还在排队，算法已经走到B，上报A时就可能错拿B的标签。
AI_CPU路径把快照与SQE（设备任务描述项）关联，提交时使用实际stream/task身份；缓存复制也同步处理标签。

这属于软件元数据记录，不为打点新增设备任务、不主动同步NPU，也不改通信算法。
但它仍有CPU处理和日志写出成本，不能说零开销。

### 3. 任务与语义怎样关联

普通任务按实际node/device/stream/task及兼容任务类型精确匹配；FFts还要识别父任务及context。
公开调用则通过DB/API连接证据、类型/大小、实际参与Rank及可验证区间绑定，不能按“第几个调用”猜。
不使用时间最近、任务ID偏移或Rank推设备的补配方式。

关联后形成`merged.csv`，同时保留成功关联、只有profiler任务、未匹配语义及歧义。
所以它不是只剩异常的表，也不是每个普通计算任务都有通信标签。

**“语义100% exact”是这些语义记录匹配正确，不是所有任务都有语义，更不是定位准确率100%。**

### 4. 依赖关系怎样来

`merged.csv`主要是任务事实，不是已经列好的依赖边。构图阶段根据执行与同步证据建立关系：

| 关系 | 依据 | 必须说明的边界 |
| --- | --- | --- |
| 同一物理stream先后 | 已观察到的执行顺序 | 不能推广成所有stream之间的全序。 |
| Record→Wait同步 | 完整通知通道、两端角色和唯一配对证据 | notify ID可复用，仅ID相同不足以连边。 |
| FFts上下文顺序/同步 | 图实例、context和相应语义/观测证据 | 部分是声明顺序，不能当完整硬件DAG。 |
| 跨Rank/跨机通知 | 可验证的两端事实和对应关系 | 缺失、歧义保留断点，不补画端点。 |

明确的图产物是`dep_graph_nodes.csv`和`dep_graph_edges.csv`；边记录源、目标、类型、原因和证据等级。
`dep_graph_notify_ambiguities.csv`保留无法唯一确定的通知关系。
资源图从执行图派生，便于观察搬运、归约及等待；不是另凭时间线猜一套因果边。

可以用下面的示意解释，但须注明“只有原始证据支持时，工具才发布这条路径”：

```text
Rank 0：Copy自身变慢 -> Record较晚发生
                              |
                              | 已配对通知
                              v
Rank 1：                   Wait -> 后续任务
```

它解释为什么不能直接把Rank1的长Wait叫作Rank1故障。
这条路径也不证明Wait的全部增量都由Copy贡献，不能把所有并发Wait耗时相加当训练损失。

### 5. 怎样从图得到诊断

先确认任务和历史参考可比较，再判断自身耗时增长，最后结合源头策略及实际路径形成候选。
要区分“执行本身慢”“Host准备/发起晚”和“只观察到等待或协议区间异常”。

| 模式 | 参考 | 使用条件 |
| --- | --- | --- |
| Rolling | 同次采集前5个正式轮、相同位置和可比较结构的任务 | 需要公开调用/轮次绑定；预热、当前和未来轮不进参考。 |
| Baseline | 另一份独立正常运行 | 负载配置及调用结构可比；仍需语义、身份和通信实例证据。 |

当前Rolling使用前5轮均值、1.5倍及3MAD等规则；MAD用于衡量历史波动。下游等待观察与源头判慢分开。
Baseline另有中位数/MAD及增量门槛，不是把Rolling规则原样搬过去。
参考不足就报告不足，不能临时换参考凑出异常。

通用入口默认`legacy`。Rolling可显式用`dual`比较内部执行提案和公开Host迟到提案，
或用`dual-v2`做当前多机源头排序试验；它们不是所有用户的默认配置，也不是已校准的故障分类器。
dual-v2允许没有慢Wait传播路径的局部执行候选，因此“无路径”不能一概解释为程序漏生成了图。
Baseline当前不提供Host准备区间溯源；这类问题应优先考虑有公开观测的Rolling。

**检测回答“是否变慢”，排序回答“先查谁”，物理归因回答“为什么慢”；前两者不自动证明第三者。**

## 三、怎样使用：按六步讲

### 第一步：安装工具，确认原训练正常

```bash
git clone --branch nf --single-branch https://github.com/Keiran810975/hccl-trace.git
cd hccl-trace
python3 -m pip install -e .
hccl-diag analyze --help
```

采集端安装在原来能训练的Python环境中；离线分析端只需Python >=3.9和标准库，不需要NPU、CANN或PyTorch。
安装Python工具不会编译/部署通信库，更不会自动运行用户模型。

### 第二步：准备配套库与设备

先由管理员按本次版本准备相互匹配的Host库和实际执行路径所需的Device包，核验实际加载结果。
仅设置`LD_LIBRARY_PATH`不算证明加载成功；只更新Python也不会让旧Device自动具有新打点。
两节点使用一致源码/兼容构建，采集中途不更新库、策略或源码。

记录原包和策略，限定授权整卡，确认无他人任务、HBM正常、端口/网络/磁盘满足要求，并准备异常恢复。
新设备以真实runtime/profiler映射为准，不照抄我们的机器名、卡号、哈希或IP。

### 第三步：接入实际通信位置

在训练中用`hccl_trace.Trace`注册真实通信成员，在iteration内包住实际collective，并在训练原本已有的真实完成边界后记录completion。
SDK不执行这个同步，不能为方便绑定给每个调用偷偷增加同步，否则会改变原训练性能。
DDP/FSDP内部通信需在相应hook或适配点接入，不能只包住整个`backward()`。

最小真实设备例子见[diagnosis_collectives.py](../examples/diagnosis_collectives.py)，
SDK接入示例见[接口说明](诊断工具使用说明.md#在自己的训练中记录位置)。

### 第四步：每节点独立采集

下面是**已构建并核验配套低日志Device包之后**的模板，不是裸机部署脚本。
`ORIGINAL_LOCAL_LAUNCH_COMMAND`应事先设为本节点原训练启动命令，实际库、SDK和多机启动配置也须先就绪。
每次使用新RUN_ID；各节点共享RUN_ID，但NODE_ID和输出目录各自独立。

```bash
export RUN_ID=my-training-001 NODE_ID=nodeA
export CAPTURE="$HOME/hccl-trace-runs/captures/$RUN_ID"
export NODE_CAPTURE="$CAPTURE/nodes/$NODE_ID"
mkdir -p "$NODE_CAPTURE/plog" "$NODE_CAPTURE/calls"
export HCCL_STEP_TRACE=1
export HCCL_TRACE_RUN_ID="$RUN_ID" HCCL_TRACE_NODE_ID="$NODE_ID"
export HCCL_TRACE_CALLS_DIR="$NODE_CAPTURE/calls"
export ASCEND_PROCESS_LOG_PATH="$NODE_CAPTURE/plog"
unset ASCEND_MODULE_LOG_LEVEL
export ASCEND_GLOBAL_LOG_LEVEL=2 ASCEND_SLOG_PRINT_TO_STDOUT=0
msprof --application="$ORIGINAL_LOCAL_LAUNCH_COMMAND" \
  --output="$NODE_CAPTURE/msprof" \
  --hccl=on --task-time=l1 --ascendcl=on --ai-core=off --type=db
```

旧Device直接改WARNING曾导致必要地址/anchor丢失，不能只看到语义日志还在就认为可用。
不具备新低日志包时先按[通用教程](从零开始运行训练诊断.md)完成配套部署和原配置短采验证，不能盲用此模板。
多机还要保留采集期适用的前后校时探针，具体操作见[多机教程](从零开始运行训练诊断.md#8-多机采集每节点独立输出统一绑定)。

典型原始数据目录：

```text
captures/my-training-001/
  capture.json                 拓扑/清单，按采集实际证据配置
  nodes/nodeA/plog/             Host/AI_CPU文本日志，包含语义
  nodes/nodeA/msprof/PROF_.../   完整PROF、consolidated DB和原始元数据
  nodes/nodeA/calls/rank-N.jsonl 公开训练观测，一行一个JSON
  nodes/nodeB/...               多机各节点分别保存；另保留校时观测
```

日志时间不当设备时长；终端训练输出也不是上述原始数据的替代品。

### 第五步：汇集后在CPU上离线诊断

保留各节点完整目录和真实映射，传输后校验文件；不只复制一个DB或把后台采集混进前台。
等待全部Rank及msprof结束，并检查训练数值、语义和调用绑定。
若临时更改了Device包、设备策略或端口，应在采集结束后、CPU离线分析前按授权方案恢复并实读核验，最终再复核一次。

```bash
hccl-diag analyze --capture /path/to/captures/my-training-001 \
  --mode rolling --output /path/to/results/my-training-001 --keep-debug
```

没有足够同次历史、但有独立可比正常采集时，用：

```bash
hccl-diag analyze --capture /path/to/abnormal --baseline /path/to/normal \
  --mode baseline --output /path/to/results/abnormal --keep-debug
```

输出必须是新的、位于输入目录之外的目录。默认legacy；复现多机排序试验须在Rolling命令显式加`--source-policy dual-v2`。
`--require-clock-alignment`可要求适用校时门禁；缺校时应补采集证据，而不是事后把曲线平移到看起来对齐。

### 第六步：读报告、留证据、确认恢复

| 产物 | 讲给用户的用途 |
| --- | --- |
| `execution.html` | 看实际任务时间线、候选位置、相关依赖和Wait。 |
| `root_causes.json` | 查策略、状态、覆盖率、候选/外部线索、未归因观测及证据限制。 |
| `propagation.html` | 看候选如何沿已报告路径连接到等待，可切候选/目标Rank/分支。 |
| `结果名.debug/` | `--keep-debug`留下的关联表、图表和比较明细，便于审计。 |

看报告的顺序：**状态/覆盖率 -> 位置与单位 -> 历史/当前耗时 -> 依赖路径 -> 未解释部分与限制。**
Host区间和设备task分开；dual策略的首选可能是Host区间，不应只取`candidates[0]`当统一答案。
`--selected-iteration-view`是全量分析后取所选轮原图切片，所选轮也可能不是注入轮；不能将它叫全量原始采集。
保留全量输入和debug才能复查更多轮次；最终HTML自包含，但不代替原始DB/plog。

收尾时复核前述恢复结果。我们的普通CLI只读分析输入，不自动删除原始采集。
实验运行器的封存、注入评测、租约恢复和归档清理属于额外编排，不是每个用户都必须运行的诊断步骤。

## 四、现场演示怎么讲

建议先用已有报告演示，避免把第一次部署和大型训练当作现场演示。
真实截图及详细读图说明见[功能说明](采集打点与诊断功能说明.md#4-最终结果长什么样)。

1. 先打开`propagation.html`，指出候选的Node/Rank、iteration/调用位置和前5轮对比。
2. 选择一条实际存在的分支，指出源头、Record、Wait，解释每条箭头的证据；没有路径就展示缺口。
3. 跳到`execution.html`看同一graph_id和stream上下文，说明这不是另一张猜出来的图。
4. 展示debug中的`merged.csv`、`dep_graph_nodes.csv`、`dep_graph_edges.csv`，解释“任务明细”和“关系明细”的区别。
5. 最后看JSON的coverage、未归因观测和limitations，说明报告可被程序读取和独立复核。

使用现有801截图演示时，第三个候选有一条路径，主候选没有；不能将切换后的路径说成主候选或所有候选的证据。

## 五、必须提醒的使用事项

| 容易误解的地方 | 正确说法 |
| --- | --- |
| 任意设备拉代码就能用 | 先检查软硬件兼容、配套库实际加载及算法覆盖；主要设备证据来自CANN8.5.1，DB当前支持schema 1.2.0。 |
| 只安装Python就完成部署 | 采集还需要配套Host/Device和原训练环境；CPU离线分析才不需要这些设备依赖。 |
| 所有任务都要有通信语义 | 普通计算TASK可能只有profiler事实；我们聚焦受支持的集合通信诊断。 |
| 关闭所有非通信开关就能降开销 | 关闭TASK或ASCENDCL曾丢必要事实；低日志方案也仍采普通TASK/API，不是通信专用在线过滤。 |
| Rank、LOCAL_RANK就是设备号 | 必须核验真实runtime/profiler设备映射，多芯片卡还要区分物理整卡。 |
| API返回或Work.wait返回就是完成 | 可能只是提交/流依赖；需要训练原有且已验证的设备完成观测。 |
| 相同notify ID就存在依赖 | Notify资源可复用，需要完整通道和唯一配对；缺证据不补边。 |
| 长Wait就是网络慢 | 可能是对端执行慢或发起晚；协议区间也不等于纯网络硬件时间。 |
| 跨机图可直接算全局关键路径 | 无校时不跨机绝对时间相减；软件校时也不等于逐笔RDMA硬件完成或精确全局关键路径。 |
| CLI返回0、语义exact就定位成功 | 还要看诊断状态、参考覆盖和候选；关联正确与定位命中是不同指标。 |
| 无候选就是健康 | 可能参考不足、不可比较或缺证据；必须查看状态。 |
| 候选就是物理故障定论 | `physical_cause`可以仍为unknown；依赖解释不等于独立证明物理竞争原因。 |
| 三报告足够全量重放 | 必须另留原始输入和必要debug；删过大输入的旧实验不能承诺全量重放。 |

## 六、被问到“效果和开销怎么样”时

建议这样回答，不需要展开全部实验历史：

> 我们完成了真实单机和多机的采集、精确关联与依赖图验证，也有异常注入验证。
> 单机30组分批清单中27组任一和首选命中，但其中SDMA是固定位置重复，不能叫任意位置准确率90%。
> 旧多机4个样例在同输入离线优化后可命中，但这些数据参与过方法开发；新独立多机样例仍有漏诊，正常误报也未解决。
> 低日志新包在一个完整单机配对块中，采集相对基线约增加0.519%迭代耗时，但重复性测试未完成，不承诺所有负载都是这个开销。

不将不同配置、新旧样例、Host区间和设备task混成一个“准确率”。不使用正在运行的计划数充当已完成数。
数值、统计口径和失败分母见[功能与实验结果说明](采集打点与诊断功能说明.md#5-已经做过的实验怎样理解数字)。
进行中的新多机批次查看本工作区[动态结果索引](../artifacts/multinode19-lowlog-20261106-1000/latest-results.md)，讲解前核对日期和实际完成数。

## 七、结束时用三句话收住

> 第一，我们把真实执行、算法语义和训练位置关联起来，而不是只看一张时间线。
> 第二，沿已有依赖解释等待，并与可比较历史对照，输出能复查的候选与路径。

# 当前诊断逻辑

对应统一入口`hccl-diag analyze capture`，单机和多机自动识别。
本文说明当前默认Rolling路径，不把旧实验策略的结果当成当前默认准确率。

## 1. 先建立可信事实

```text
msprof真实任务时间 + HCOMM语义日志 + SDK公开调用/iteration/完成边界
    -> 精确关联与质量门禁
    -> 对应任务的自身耗时比较
    -> 执行慢化簇 / Host准备迟到提案
    -> 选择一个胜出簇或Host区间
    -> 展开已有依赖传播，保留其他未解释观测
```

不使用注入位置、注入类型或注入窗口选择候选。这些真值仅在独立实验评测时读取。
不按时间最近、任务序号或Rank猜设备来补配。身份不唯一、历史不足或构图不完整，保持不可比/证据边界。

节点数来自已验证的真实节点身份，不从Rank数量猜；单机八Rank仍是单机。
默认参考为当前轮之前连续五个正式轮的同位置任务，预热和当前轮不进入参考。
最初五个正式轮不评分，之后每轮滚动更新；不是全程都固定使用最初五轮。

自身慢化要求当前耗时大于参考均值，并满足：

```text
当前耗时 >= 前五轮均值 * 1.5
当前耗时 - 前五轮均值 >= 3 * MAD
```

MAD是五个历史样本相对其中位数的绝对偏差中位数，不是标准差。
持续异常可能污染后续滚动参考；当前规则也没有经过一般负载的低误报率校准。

## 2. 调用前延迟怎么发现

这条路径找的是Host准备区间，不是设备kernel。

1. SDK/适配器显式记录准备开始和集合通信调用前边界。
   区间由真实观测定义，不把两次通信之间的全部空闲时间自动解释成准备。
2. 经公开调用、类型/数据量、真实完成边界和唯一API关联，找到对应HCCL调用。
   Python异步返回不算设备完成。
3. 比较相同Rank、通信位置在前五轮的准备耗时，检查1.5倍及3MAD慢化。
4. 检查同次调用的真实通知生产端和其他Rank的慢Wait是否唯一配对。
   对端Wait也须满足严格慢化条件；准备区间与等待应有可证实的正重叠。
5. 同机要求exact Notify证据；跨机要求唯一observed协议依赖及独立校时，
   正重叠须超过双方估计误差余量。没有足够校时，不跨机直接相减。

满足条件才形成可竞争的Host迟到提案，再与执行慢化簇比较。
缺少准备观测、历史或通知支持，不能凭“某Rank晚了”补出Host根因。

结果定位到`Node / Rank / iteration / 调用位置 / Host时间区间`。
`stream_id`、`task_id`为null；图中Record/RDMA生产端只是关联锚点，不是Host任务，
也不新增Host到设备的虚构依赖边。

它能支持“这个Rank调用前准备迟到并关联到对端等待”，但不能仅凭此区分
sleep、CPU调度、数据准备或上游计算等物理原因。

## 3. 其他异常怎么发现

这条路径从HCCL内部任务自身执行耗时增长出发，不直接猜物理异常类型。

| 实验注入类型 | 诊断器实际观察 | 可以输出什么 | 不能直接保证什么 |
|---|---|---|---|
| SDMA竞争 | 内部Copy/SDMA自身变慢 | 慢执行任务簇及已有传播路径 | 自动证明是外部Copy抢资源 |
| 通信竞争 | 内部搬运/归约等执行变慢 | 源头候选位置、任务与等待关联 | 仅凭时间确定哪个后台通信造成竞争 |
| RoCE限速 | 内部任务、协议区间或Wait变慢 | 有自身执行增长时可能选出任务；其他慢Wait保留观测 | 把RDMA提交耗时当传输耗时，或必然定位到网口限速 |
| 计算竞争 | 可能表现为Host准备迟到或内部执行增长 | 仅输出有实际证据的区间/任务 | 自动确认外部GEMM或具体计算进程 |

当前执行源头集合包括已证明HCCL归属的SDMA、Inline Reduce及受支持的混合计算任务。
RDMA提交不是硬件传输完成时间，所以不能把它的API/doorbell时长直接作为网络根因。
Wait变长只说明等待增加，不自动把Wait当源头；若只有Wait/协议变慢而没有足够执行或Host证据，
当前默认路径可能无法定位，报告必须保留未解释观测。

### 单机选择

先找满足自身慢化条件的内部执行任务，再按真实依赖上下文形成局部簇。
簇内要求相同Node/device/Rank/调用/iteration，正常资源任务会分隔簇；
不会仅因时间相近就把任务合在一起。

评分考虑相对增长、历史波动/过去报警频率、不同stream/任务类型的共同变化和时间密度，
传播只作有限支持。先取局部Top1簇，再与严格Host提案比较相对增长分。

### 多机选择

保留原局部依赖簇，再用同Node/device/Rank/通信域/iteration的完整内部执行任务群慢化倍数P95
辅助排序。任务群包含正常可比任务，不只计算已经筛出的慢任务。
至少20个任务且全部前五轮身份完整才提供P95支持，否则保持中性，不猜测缺失值。

P95支持乘子为`1 + ln(max(1, P95))`，不是单独的候选准入门槛，也不改变原簇或1.5倍/3MAD条件。
执行提案再与严格Host提案比较。该排序在已知SDMA开发样本上较好，
但通信竞争、RoCE定位及正常误报仍有未解决问题。

## 4. 传播与最终报告

对已选源头，只沿原图中允许的同流顺序和唯一Notify关系展开，并检查时间及校时限制。
下游Wait采用独立的20%/3MAD传播观察门槛；Host提案准入仍要求更严格的慢Wait支持，不能混用。
遇到另一处自身执行增长、正常Wait、缺边或歧义等边界时，不把其全部耗时归给前面的候选。
传播证据不是逐个源头的实测因果贡献，多个Wait增量不能相加成训练损失。
没有传播路径的自身执行增长也可以作为候选，但必须明确没有证明慢Wait传播。

目前只发布一个胜出执行簇或Host区间，簇内候选平行，没有“主候选”。
这不保证同时保留多个独立故障；其他提案在debug审计中，未关联所选源头的慢Wait另列观测。

- `execution.html`：候选所在正式轮的原图切片与通信显示区间。
- `root_causes.json`：候选位置、实际/参考耗时、慢化、质量及完整未归因观测。
- `propagation.html`：已有传播路径、逐跳证据和有界未归因预览。

新报告不展示关键路径模型收益。默认`physical_cause`仍可能为`unknown`，
定位到慢任务不等于已经证明它由哪种物理资源故障造成。

显式`--baseline normal`使用独立正常采集的中位数，当前主要覆盖执行任务比较，
不能把这条路径当作已完整支持Host准备迟到。使用前提见[统一采集与诊断](统一采集与诊断.md)。
